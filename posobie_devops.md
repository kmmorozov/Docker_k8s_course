## Модуль 1. Введение в DevOps

### 1.1. Что такое DevOps

**DevOps** — это набор практик, культуры и инструментов, который объединяет **разработку (Development)** и **эксплуатацию (Operations)** в единый цикл создания ПО. Цель — ускорить выпуск качественного продукта, сократив разрыв между командами.

Историческая проблема: разработчики писали код и «передавали его через стену» администраторам, которые вручную разворачивали его на серверах. Каждый этап — отдельные инструменты, отдельные циклы, частые сбои при релизах.

**Ключевые принципы DevOps (модель CAMS):**
- **Culture (культура)** — общая ответственность за продукт у разработки и эксплуатации.
- **Automation (автоматизация)** — всё, что делается вручную более одного раза, должно быть автоматизировано (сборка, тесты, деплой).
- **Measurement (измеримость)** — всё измеряется метриками, а не ощущениями.
- **Sharing (обмен знаниями)** — общие инструменты, общие каналы связи, общие ритуалы.

Термин **CI/CD** — неотъемлемая часть DevOps: **Continuous Integration** (непрерывная интеграция), **Continuous Delivery/Deployment** (непрерывная поставка/развёртывание).

### 1.2. Проблемы, которые решает DevOps

Типичные проблемы классической модели и их решение:

| Проблема | Последствие | Решение DevOps |
|---|---|---|
| Ручной деплой | Ошибки, долгие релизы | Автоматизация развёртывания |
| «У меня на машине работает» | Расхождение окружений | Контейнеры, инфраструктура как код |
| Редкие большие релизы | Страх изменений | Частые мелкие релизы |
| Долгое обнаружение проблем | Простои | Мониторинг, алёртинг, метрики |
| Разные инструменты у команд | Конфликты, потери информации | Единый toolchain |

### 1.3. Критерии оценки DevOps (метрики DORA)

**DORA (DevOps Research and Assessment)** — стандарт индустрии для оценки зрелости DevOps. Четыре ключевые метрики:

1. **Deployment Frequency (частота развёртывания)** — как часто выкатывается код в продакшен. Элитные команды — несколько раз в день.
2. **Lead Time for Changes (время от коммита до прода)** — от момента фиксации изменения до его работы у пользователя.
3. **Change Failure Rate (доля неудачных изменений)** — процент релизов, вызвавших инциденты.
4. **Time to Restore Service (время восстановления, MTTR)** — как быстро восстанавливается сервис после сбоя.

Дополнительно практикуют пятый сигнал — **Reliability** (надёжность в отношении пользовательских ожиданий: SLI/SLO/SLA).

### 1.4. Преимущества DevOps

- **Скорость**: автоматизированный конвейер сокращает цикл «идея → прод» с месяцев до часов.
- **Надёжность**: автоматические тесты и проверки на каждом шаге снижают число дефектов.
- **Воспроизводимость**: инфраструктура и окружения описаны кодом и поднимаются одинаково в любой среде.
- **Масштабируемость**: контейнеризация и оркестрация позволяют расти без ручной настройки серверов.
- **Культура без страха**: частые мелкие релизы легко откатываются.

## Модуль 2. Архитектура ПО. Микросервисы

### 2.1. Архитектура ПО

**Архитектура ПО** — это высокоуровневое структурное описание системы: из каких компонентов она состоит, как они взаимодействуют, как распределяются ответственность и данные.

Основные подходы:

**Монолит** — всё приложение (UI, бизнес-логика, доступ к данным) единое целое, разворачивается как один артефакт.
- Плюсы: простая разработка и деплой на старте, лёгкий дебаг, нет сетевых вызовов внутри.
- Минусы: по мере роста кода — сложно поддерживать, масштабируется только целиком, технологический стек «заморожен».

**Микросервисная архитектура** — приложение разбито на небольшие, независимо развёртываемые сервисы, каждый со своей зоной ответственности и (обычно) своей базой данных.

### 2.2. Микросервисы

**Микросервис** — автономный компонент, который:
- реализует одну бизнес-способность (заказы, платежи, уведомления);
- развёртывается независимо;
- общается с другими по сети через API (обычно HTTP/REST или gRPC, для событий — брокеры сообщений);
- владеет своими данными.

Плюсы микросервисов:
- **Независимые релизы** — обновляем только один сервис.
- **Изолированные сбои** — падение сервиса уведомлений не роняет оформление заказа (при правильной обработке).
- **Разный стек технологий** — каждый сервис пишется на подходящем языке.
- **Гранулярное масштабирование** — нагруженный сервис реплицируется отдельно.

Минусы (их нужно знать честно):
- Распределённая сложность: сеть нестабильна, нужны таймауты, ретраи, идемпотентность.
- Распределённое хранение данных: сложные транзакции решаются паттернами Saga, outbox.
- Накладные расходы на инфраструктуру: оркестрация, логирование, трассировка, service discovery.

**Паттерн «База данных на сервис» (Database per Service)** — каждый сервис работает только со своей БД; прямой доступ к чужой БД запрещён. Обмен данными — только через API сервиса.

### 2.3. Выбор архитектуры

Практические ориентиры:

- **Начинайте с монолита (или модульного монолита)**, если команда маленькая и домен ещё не устоялся. Преждевременный микросервисный распил — частая причина провалов.
- **Переходите к микросервисам**, когда появляются явные признаки: разные части системы требуют разного масштабирования, разные команды мешают друг другу в одном репозитории, часть системы должна жить на другом стеке.
- Правило **Single Responsibility**: границы сервисов проводятся вокруг бизнес-возможностей (bounded contexts из DDD), а не технических слоёв.

**Методология «12 факторов» (The Twelve-Factor App)** — набор практик для приложений, которые будут работать в облачных/контейнерных средах. Ключевые факторы, важные для курса:
- **I. Codebase** — одна кодовая база, много развёртываний.
- **III. Config** — конфигурация в переменных окружения, **никогда не хардкодить секреты в коде**.
- **IV. Backing services** — БД, брокеры очередей — присоединяемые ресурсы, доступные по URL из конфигурации.
- **VI. Processes** — приложение без состояния (stateless), состояние — во внешнем хранилище.
- **VII. Port binding** — сервис публикуется через порт, экспортируемый приложением.

## Модуль 3. Система контроля версий. Основы Git

### 3.1. Что такое Git и его появление

**Git** — распределённая система контроля версий (DVCS), созданная Линусом Торвальдсом в 2005 году для управления исходным кодом ядра Linux.

Git хранит не разницу файлов, а **снимки (snapshots) проекта** на каждый коммит: кто, когда, что изменил, со ссылкой на предыдущее состояние.

### 3.2. Centralized VCS и Distributed VCS

**Централизованные VCS (CVCS)** — SVN, CVS, Perforce. Один центральный сервер хранит историю; разработчики работают с ним напрямую. Минус: сервер — единая точка отказа, работать офлайн нельзя.

**Распределённые VCS (DVCS)** — Git, Mercurial. У каждого разработчика — полная копия репозитория со всей историей. Можно коммитить, ветвиться и смотреть историю без сети; центральный сервер нужен только для обмена между копиями.

### 3.3. Устройство Git

Ключевые области рабочего процесса:

- **Рабочая директория (Working directory)** — файлы, с которыми вы работаете.
- **Индекс / Staging area** — подготовленные к коммиту изменения (`git add`).
- **Локальный репозиторий** — база коммитов (каталог `.git/`).
- **Удалённый репозиторий** — общая копия на сервере (GitLab, GitHub).

Внутреннее устройство `.git/`: объекты **blob** (содержимое файла), **tree** (каталог), **commit** (точка истории со ссылками на дерево и родителей), **tag** (подписанная метка). Коммиты образуют направленный ациклический граф. **Ветка — это просто указатель (ссылка) на коммит**, поэтому создание и переключение веток мгновенны.

### 3.4. Основные команды

Начало работы и фиксация изменений:

```bash
# Настройка идентичности (выполняется один раз на машину)
git config --global user.name "Ivan Petrov"
git config --global user.email "ivan.petrov@example.com"

# Создание нового репозитория в текущей директории
git init

# Клонирование существующего репозитория
git clone https://gitlab.example.com/devops/demo-app.git

# Просмотр состояния рабочей директории и индекса
git status

# Добавить конкретный файл в индекс
git add app.py
# Добавить все изменения текущей директории
git add .
# Убрать файл из индекса, не трогая сам файл
git reset HEAD app.py

# Создать коммит из проиндексированных изменений
git commit -m "feat: add health check endpoint"

# Просмотр истории
git log --oneline --graph --decorate --all
```

### 3.5. Работа с ветками

**Ветвление (branching)** — основной инструмент параллельной работы. Типовой процесс: ветка `main` — стабильный код, ветки `feature/*` — разработка, `hotfix/*` — срочные исправления.

```bash
# Список локальных веток; * — текущая
git branch

# Создать ветку (но не переключаться)
git branch feature/login

# Создать ветку и сразу переключиться на неё
git checkout -b feature/login
# Эквивалент в современном синтаксисе
git switch -c feature/login

# Переключиться на существующую ветку
git checkout main
git switch main

# Удалить ветку (после слияния)
git branch -d feature/login
# Принудительно удалить, даже если не слита
git branch -D feature/login

# Слить ветку feature/login в текущую
git merge feature/login

# Интеграция через rebase: переносит коммиты текущей ветки
# поверх указанной — история получается линейной
git rebase main
```

**Merge vs Rebase.** `merge` создаёт коммит слияния и сохраняет реальную историю параллельной работы — безопасно для общих веток. `rebase` переписывает историю, делая её линейной — удобно для локальных веток перед пушем, **но нельзя делать rebase уже опубликованных коммитов**.

Разрешение конфликтов: при конфликте Git помечает файл маркерами `<<<<<<<`, `=======`, `>>>>>>>`. Открываете файл, оставляете нужный вариант, затем `git add файл` и `git commit` (или `git rebase --continue` при rebase).

### 3.6. Работа с удалёнными репозиториями

```bash
# Список удалённых репозиториев
git remote -v

# Добавить удалённый репозиторий
git remote add origin https://gitlab.example.com/devops/demo-app.git

# Отправить ветку main на origin (-u запоминает связь для git push/pull без аргументов)
git push -u origin main

# Забрать изменения с сервера, не меняя рабочую директорию
git fetch origin
# Забрать и сразу слить в текущую ветку (fetch + merge)
git pull origin main
# То же, но через rebase — линейная история
git pull --rebase origin main
```

### 3.7. Дополнительные команды

```bash
# Отложить незакоммиченные изменения и вернуть чистую директорию
git stash
git stash list            # список отложенных изменений
git stash pop             # применить последнее и удалить из списка
git stash apply stash@{0} # применить конкретное, не удаляя

# Взять отдельный коммит из другой ветки в текущую
git cherry-pick a1b2c3d

# Отменить коммит, создав новый обратный (безопасно для истории)
git revert a1b2c3d

# Переместить указатель ветки на другой коммит (локальная история!)
git reset --soft HEAD~1   # сдвинуть, изменения останутся в индексе
git reset --mixed HEAD~1  # сдвинуть, изменения останутся в рабочей директории
git reset --hard HEAD~1   # сдвинуть и выбросить изменения (осторожно!)

# Журнал всех перемещений указателей — «спасательный круг»
git reflog

# .gitignore — файлы, которые Git игнорирует
cat > .gitignore <<'EOF'
# Python
__pycache__/
*.pyc
.venv/
# IDE
.idea/
.vscode/
# Секреты и окружение — НИКОГДА не коммитить!
.env
*.pem
*.key
# Сборка
dist/
build/
EOF
```

**Правила хорошего тона:** коммитить часто и маленькими логически цельными порциями; писать осмысленные сообщения; не коммитить секреты, бинарники и файлы окружения.

### 3.8. Углублённый разбор: тонкости команд Git

**HEAD~n и HEAD^n — разные вещи.** `HEAD~2` — два коммита назад по цепочке первых родителей; `HEAD^2` — второй родитель коммита слияния (тот, что влили). Символ `~` идёт «вглубь по линии», `^` — «к конкретному родителю»: `HEAD~2^2` — второй родитель коммита двумя шагами ранее.

**Просмотр изменений — `git diff` на все случаи:**

```bash
git diff                      # рабочая директория vs индекс (непроиндексированное)
git diff --staged             # индекс vs HEAD (что войдёт в коммит)
git diff HEAD                 # рабочая директория vs HEAD (всё вместе)
git diff main...feature       # изменения feature относительно ТОЧКИ РАСХОЖДЕНИЯ (три точки — то, что покажет MR)
git diff main..feature        # разница кончиков веток (две точки) — при разошедшихся ветках вводит в заблуждение
git show a1b2c3d              # коммит целиком: метаданные + патч
```

**Продвинутый поиск по истории:**

```bash
git log --oneline --graph --all        # граф всех веток с указателями
git log --stat -n 10                   # история + статистика файлов по каждому коммиту
git log --author="petrov" --since="2 weeks ago"
git log --grep="hotfix"                # поиск по сообщениям коммитов
git log -S "function login"            # pickaxe: коммиты, где строка появилась или исчезла
git log --follow -- old.py             # история файла С учётом переименований
git shortlog -sn                       # кто сколько коммитил
git blame app.py                       # кто и когда изменил каждую строку файла
```

**Современные команды восстановления** (вытесняют старый универсальный `checkout`):

```bash
git restore app.py              # откатить НЕпроиндексированные изменения файла (бывший checkout --)
git restore --staged app.py     # убрать файл из индекса (бывший reset HEAD)
git restore --source=main~3 app.py   # вернуть версию файла из старого коммита
git rm --cached secret.env      # перестать отслеживать файл, оставив его на диске
git mv old.py new.py            # переименование с сохранением истории (--follow её видит)
git clean -fd                   # удалить untracked файлы и каталоги (-x — и игнорируемые; осторожно!)
```

**Теги — фиксация версий.** Различают лёгкие (просто указатель на коммит) и аннотированные (полноценный объект с автором, датой и сообщением — для релизов):

```bash
git tag -l "v1.*"                      # список с фильтром
git tag -a v1.4.0 -m "Release 1.4.0"   # аннотированный тег на текущем коммите
git tag v1.4.1 a1b2c3d                 # лёгкий тег на конкретном коммите
git push origin v1.4.0                 # тег НЕ улетает с обычным push — пушить явно
git push origin --tags                 # все теги разом
git tag -d v1.4.0 && git push origin :refs/tags/v1.4.0   # удалить локально и на сервере
```

**Интерактивный rebase** — причёсывание истории перед публикацией: `git rebase -i main` откроет список коммитов с командами: `pick` (оставить), `reword` (переименовать сообщение), `squash` (слить с предыдущим, объединив сообщения), `fixup` (слить, выбросив сообщение), `edit` (остановиться и доработать), `drop` (удалить). Удобная связка «исправление + автоподбор»: `git commit --fixup a1b2c3d` → `git rebase -i --autosquash main` — fixup-коммиты сами встанут на место и пометятся как fixup.

**Тонкость конфликтов при rebase:** вы «прилетаете» на чужую ветку, поэтому во время rebase **«ours» — это то, поверх чего перебазируетесь, а «theirs» — ваши изменения** — ровно наоборот по сравнению с merge (`git checkout --ours` при rebase оставит main, а не вашу ветку).

**Безопасный force-push:**

```bash
git push --force-with-lease origin feature/login
```

`--force-with-lease` отклонит пуш, если на сервере появились коммиты, которых нет в вашей копии, — не затирает чужую работу, в отличие от голого `--force`. **Правило: force-push допустим только в свои feature-ветки и никогда в защищённые (`main`).**

**Стратегия pull:** `git config --global pull.rebase true` — по умолчанию тянуть через rebase, без коммитов слияния «Merge branch 'main'». `git pull --rebase` эквивалентна связке `git fetch` + `git rebase origin/main`. Для длинноживущих веток лучше регулярно `git rebase origin/main` (или `git merge origin/main`), чтобы конфликты решать маленькими порциями, а не одним огромным при слиянии.

**Поиск поломавшего коммита бинарным поиском:**

```bash
git bisect start
git bisect bad                 # текущее состояние сломано
git bisect good v1.3.0         # этот тег работал
# Git переключает на середину интервала — проверяем и отвечаем good/bad; итераций ≈ log2(N)
git bisect reset               # вернуться к исходной точке
```

**Stash глубже:**

```bash
git stash push -m "WIP: login form"   # с сообщением (список станет читаемым)
git stash push -u                     # включая untracked файлы (по умолчанию они игнорируются!)
git stash push --keep-index           # оставить индекс как есть, отложив только рабочую директорию
git stash branch feature/new          # применить stash и сразу создать на нём ветку
git stash drop stash@{1}              # удалить конкретный (без применения)
```

**Восстановление «потерянного» коммита через reflog** — коммит без ветки не исчезает сразу (пока не отработает gc):

```bash
git reflog                            # журнал перемещений HEAD: HEAD@{0}, HEAD@{1}, …
git branch rescue HEAD@{3}            # отрастить ветку на найденный коммит
# или полный откат состояния: git reset --hard HEAD@{1}
```

**Подмодули** (кратко) — внешние репозитории внутри вашего; коммит суперпроекта фиксирует конкретный коммит подмодуля:

```bash
git submodule add https://github.com/org/shared-lib.git libs/shared-lib
git submodule update --init --recursive   # после клонирования основного репозитория
git diff --submodule=log                  # какие коммиты обновились в подмодулях
```

## Модуль 4. Docker

### 4.1. Что такое Docker

**Docker** — платформа контейнеризации, позволяющая упаковать приложение вместе со всеми зависимостями в единый переносимый артефакт — **образ (image)** — и запускать его изолированно в **контейнере**.

Решает проблему «работает на моей машине»: образ содержит всё нужное — интерпретатор, библиотеки, код, конфигурацию. Контейнер одинаково запускается на ноутбуке разработчика, тестовом и продакшен-сервере.

### 4.2. Виртуализация и контейнеризация

**Виртуализация (ВМ)** — гипервизор (VMware, KVM, Hyper-V) эмулирует аппаратуру и запускает полноценные гостевые ОС. Каждая ВМ несёт собственное ядро — накладные расходы на память и запуск (минуты).

**Контейнеризация** — контейнеры делят ядро хостовой ОС, изолируясь на уровне процессов. Контейнер — это просто изолированный процесс, стартующий за миллисекунды и потребляющий минимум ресурсов.

Технологии, на которых построен Docker:
- **Namespaces (пространства имён)** — изоляция видимости: каждый контейнер видит только свои процессы (PID), сетевые интерфейсы (NET), файловую систему (MNT), пользователей (USER).
- **Control Groups (cgroups)** — лимиты и учёт ресурсов: CPU, память, I/O.

### 4.3. Экосистема Docker

- **Docker Engine (dockerd)** — демон, управляющий образами, контейнерами, сетями и томами.
- **Docker Client (docker)** — CLI, через который пользователь общается с демоном по REST API.
- **Docker Hub** — публичный реестр образов (nginx, python, postgres и т.д.).
- **Docker Registry** — сервис хранения образов; может быть приватным (см. 4.8).
- **Docker Compose** — инструмент описания многоконтейнерных приложений (модуль 5).

### 4.4. Объекты Docker

- **Image (образ)** — неизменяемый шаблон для создания контейнеров (read-only слои).
- **Container (контейнер)** — запущенный экземпляр образа (верхний слой — записываемый).
- **Volume (том)** — постоянное хранилище данных вне контейнера.
- **Network (сеть)** — изолированная сеть для связи контейнеров.

```bash
# Список локальных образов
docker images
# Список запущенных контейнеров
docker ps
# Список всех контейнеров, включая остановленные
docker ps -a
# Список томов и сетей
docker volume ls
docker network ls
```

### 4.5. Работа с контейнерами

```bash
# Запустить контейнер из образа (если образа нет — скачает из Docker Hub)
# -d — фоновый режим (detached), --name — имя контейнера, -p — проброс портов хост:контейнер
docker run -d --name web -p 8080:80 nginx

# Запуск с интерактивным терминалом и удалением контейнера после выхода
docker run -it --rm ubuntu:22.04 bash

# Остановить и запустить
docker stop web
docker start web

# Перезапуск, пауза, удаление
docker restart web
docker pause web && docker unpause web
docker rm web            # удалить остановленный контейнер
docker rm -f web         # принудительно остановить и удалить

# Просмотр логов (-f — следить в реальном времени, как tail -f)
docker logs -f web

# Выполнить команду внутри работающего контейнера
docker exec -it web bash
# Запустить psql внутри контейнера postgres
docker exec -it postgres psql -U admin -d mydb

# Скопировать файлы между контейнером и хостом
docker cp web:/etc/nginx/nginx.conf ./nginx.conf
docker cp ./index.html web:/usr/share/nginx/html/index.html

# Просмотр потребления ресурсов
docker stats

# Информация о контейнере (IP, mounts, config)
docker inspect web
# Достать конкретное поле из inspect
docker inspect -f '{{.NetworkSettings.IPAddress}}' web

# Очистка: удалить остановленные контейнеры, неиспользуемые образы, тома, сети
docker system prune -a --volumes   # осторожно: необратимо
```

### 4.6. Настройка Docker daemon

Демон настраивается через файл **`/etc/docker/daemon.json`** (после изменения — `sudo systemctl restart docker`).

```json
{
  "data-root": "/var/lib/docker",          // где хранить образы и контейнеры
  "log-driver": "json-file",               // драйвер логов
  "log-opts": {
    "max-size": "10m",                     // ротация: максимум 10 МБ на файл лога
    "max-file": "3"                        // хранить не более 3 файлов
  },
  "storage-driver": "overlay2",            // драйвер хранилища слоёв
  "insecure-registries": ["registry.local:5000"],  // реестры по HTTP без TLS
  "registry-mirrors": ["https://mirror.example.com"],
  "dns": ["8.8.8.8", "1.1.1.1"],           // DNS для контейнеров
  "live-restore": true                     // не останавливать контейнеры при рестарте демона
}
```

Управление сервисом: `sudo systemctl status docker`, `sudo systemctl restart docker`, `sudo dockerd` (ручной запуск для отладки).

### 4.7. Private Docker Registry

Чтобы хранить образы внутри компании, поднимают приватный реестр — сам контейнер `registry:2`.

```bash
# Запуск приватного реестра на порту 5000
docker run -d --name registry -p 5000:5000 --restart always \
  -v registry-data:/var/lib/registry \
  registry:2

# Тегирование образа под приватный реестр: host:port/имя:тег
docker tag myapp:1.0 localhost:5000/myapp:1.0

# Загрузка образа в приватный реестр
docker push localhost:5000/myapp:1.0

# Загрузка образа из него
docker pull localhost:5000/myapp:1.0

# Просмотр каталога образов реестра
curl -s http://localhost:5000/v2/_catalog
curl -s http://localhost:5000/v2/myapp/tags/list
```

### 4.8. Сборка образов Docker

Образ собирается по инструкциям из файла **Dockerfile** — по одному слою на инструкцию; слои кешируются, поэтому **редко меняющиеся инструкции ставят выше**.

Основные инструкции:

| Инструкция | Назначение |
|---|---|
| `FROM` | Базовый образ, обязательная первая инструкция |
| `RUN` | Выполнить команду при сборке (установка пакетов) |
| `COPY` / `ADD` | Копировать файлы из контекста сборки в образ |
| `WORKDIR` | Рабочая директория для последующих инструкций |
| `ENV` | Переменные окружения в образе |
| `ARG` | Аргументы сборки (передаются через `--build-arg`) |
| `EXPOSE` | Документирует порт контейнера (не публикует!) |
| `CMD` | Команда по умолчанию при запуске (переопределяется аргументами docker run) |
| `ENTRYPOINT` | Основная команда контейнера (не переопределяется, дополняется) |
| `VOLUME` | Точка монтирования тома |
| `USER` | Пользователь, от которого запускаются процессы |

Пример: простое Python-приложение.

```dockerfile
# Базовый образ с интерпретатором Python
FROM python:3.12-slim

# Метаданные
LABEL maintainer="devops@example.com"

# Не буферизовать вывод Python — логи сразу видны в docker logs
ENV PYTHONUNBUFFERED=1

# Рабочая директория внутри образа
WORKDIR /app

# Сначала копируем ТОЛЬКО файл зависимостей —
# слой с установкой пакетов закешируется и не будет пересобираться
# при каждом изменении кода
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# Теперь копируем код приложения
COPY app.py .

# От какого пользователя запускать (не root!)
RUN useradd -m appuser && chown -R appuser /app
USER appuser

# Документируем порт приложения
EXPOSE 8000

# Команда запуска по умолчанию
CMD ["python", "app.py"]
```

```bash
# Сборка образа: -t имя:тег, . — контекст сборки
docker build -t myapp:1.0 .
docker build -t myapp:1.0 --build-arg VERSION=1.0 .   # с аргументами сборки
docker build --no-cache -t myapp:1.0 .                # без кеша

# Запуск собранного образа
docker run -d --name myapp -p 8000:8000 myapp:1.0
```

> Dockerfile этого примера — `examples/04-docker/python-app/Dockerfile` в репозитории курса.

### 4.9. Хорошие практики сборки

1. **Один контейнер — один процесс** (главный PID 1).
2. **Не запускать от root** — создайте пользователя (`USER`) и дайте ему права только на нужные файлы.
3. **Многоэтапная сборка (multi-stage build)** — финальный образ содержит только артефакты, без компиляторов и dev-зависимостей.
4. **Копируйте минимум**: `.dockerignore` исключает из контекста сборки `node_modules`, `.git`, локальные `.env` и прочее.
5. **Порядок инструкций**: редко меняющееся (зависимости) — выше, код — ниже, для попадания в кеш.
6. **Пиньте версии базовых образов** (`python:3.12-slim`, а не просто `python`).

Пример multi-stage сборки приложения на Go:

```dockerfile
# Этап 1: сборка (образ с компилятором — большой, в финал не попадёт)
FROM golang:1.22 AS builder
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
# Статическая сборка — не нужны библиотеки в рантайме
RUN CGO_ENABLED=0 go build -o /bin/server ./cmd/server

# Этап 2: финальный минимальный образ
FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=builder /bin/server /server
USER nonroot
EXPOSE 8080
ENTRYPOINT ["/server"]
```

Файл `.dockerignore` для копипаста:

```
.git
.gitignore
*.md
.env
.env.*
node_modules
__pycache__
*.pyc
tests
Dockerfile
docker-compose*.yml
```

### 4.10. Docker Compose (обзор)

Compose позволяет описать несколько контейнеров в одном декларативном файле и управлять ими как единым приложением. Подробный разбор — в модуле 5.

```bash
# Быстрый старт: поднять app + БД одной командой
```

### 4.11. Углублённый разбор: флаги `docker run` и тонкости сборки

**Ключевые флаги `docker run`:**

| Флаг | Что делает | Тонкость |
|---|---|---|
| `-d` | Фоновый режим (detached) | Без `-d` терминал «зависает» в выводе PID 1; пары с `-it` для демонов не нужен |
| `-it` | Интерактивный псевдотерминал | Без TTY некоторые программы (bash, python REPL) молчат или падают |
| `--rm` | Удалить контейнер после остановки | Незаменим для отладочных запусков — не плодит `docker ps -a` |
| `--name` | Имя контейнера | Имя уникально: второй контейнер с тем же именем не запустится |
| `-p` | Публикация портов | `-p 127.0.0.1:8080:80` — только с localhost; `-p 8080` — случайный порт хоста |
| `-e` / `--env-file` | Переменные окружения | Перекрывают `ENV` образа; `--env-file .env` удобен в CI |
| `-v` / `--mount` | Монтирование | `--mount` — явный самодокументируемый синтаксис (type/src/dst) |
| `--restart` | Политика перезапуска | Различия — ниже |
| `--network` | Сеть контейнера | DNS по имени контейнера работает только в пользовательском bridge |
| `--user` | UID запуска | Перекрывает `USER` образа; упадёт без прав на файлы — типичная боль с volume |
| `--entrypoint` | Заменить ENTRYPOINT | `docker run --entrypoint sh image -c 'cmd'` — приём для отладки |
| `--read-only` | Корневая ФС только чтение | Пары с `--tmpfs /tmp` для временных файлов |
| `--add-host` / `--dns` | Записи в /etc/hosts, DNS | Полезно для имитации внешних имён на стенде |

**Политики перезапуска `--restart`:**
- `no` — никогда (по умолчанию);
- `always` — перезапускать всегда, **даже если остановили вручную**, и после рестарта демона;
- `unless-stopped` — как `always`, но **ручная остановка (`docker stop`) уважается**: после рестарта демона такой контейнер сам не поднимется;
- `on-failure` — только при ненулевом коде выхода (полезно для разовых задач с ретраями).

**Порты и публикация:**

```bash
docker run -d -p 8080:80 nginx                 # 0.0.0.0:8080 -> 80 контейнера (доступен извне!)
docker run -d -p 127.0.0.1:8080:80 nginx       # только с этой машины — безопаснее для отладки
docker run -d -P nginx                         # опубликовать ВСЕ порты из EXPOSE на случайные порты хоста
docker port web                                # какие порты и куда проброшены
docker run -d --expose 9000 nginx              # только внутренняя видимость порта, без публикации
```

**Тома: bind mount vs named volume vs tmpfs:**

```bash
# Bind mount — файл/каталог хоста «вживлен» в контейнер (тот же inode)
docker run -v $(pwd)/src:/app/src -v $(pwd)/nginx.conf:/etc/nginx/nginx.conf:ro myapp
# :ro — read-only внутри контейнера

# Named volume — управляется Docker'ом, живёт в /var/lib/docker/volumes, переживает контейнер
docker run -v db-data:/var/lib/postgresql/data postgres:16

# Явный синтаксис --mount (рекомендуется в скриптах)
docker run --mount type=bind,src=$(pwd),dst=/app,readonly myapp
docker run --mount type=volume,src=db-data,dst=/var/lib/postgresql/data postgres:16
docker run --tmpfs /run:rw,noexec,nosuid,size=64m myapp   # tmpfs — только в памяти, не на диске
```

**Тонкость прав на bind mount**: контейнер видит UID владельца файла с хоста как есть. Контейнер под UID 1000 и файлы хоста с UID 1000 — «один человек» (имя внутри контейнера может быть любым). Частый сюрприз: код поправили с хоста, а контейнер отвечает «permission denied» при записи.

**`docker exec` vs `docker attach`:** `exec` запускает **новый** процесс внутри работающего контейнера (стандарт для отладки: `docker exec -it web sh`); `attach` подключает терминал к **PID 1** — вы видите его вывод и шарите stdin; выход без остановки контейнера — `Ctrl+P Ctrl+Q` (иначе `Ctrl+C` убьёт главный процесс).

**Остановка контейнера — сигналы и таймаут:** `docker stop` шлёт PID 1 **SIGTERM**, ждёт 10 секунд, затем **SIGKILL**. Приложение обязано корректно обрабатывать SIGTERM (закрыть соединения, дописать данные). Таймаут меняют: `docker stop -t 30 web` или `--stop-timeout` при запуске. Проверить, что код выхода 143 (=128+15) — процесс получил SIGTERM.

**Логи — флаги и драйверы:**

```bash
docker logs -f --tail 100 --since 10m -t web    # следить, хвост 100 строк, за 10 минут, с метками времени
docker logs --until 2024-06-01T12:00:00 web
docker events                                   # события демона в реальном времени: старты, убийства, сборки
```

Драйвер по умолчанию `json-file` пишет в `/var/lib/docker/containers/<id>/<id>-json.log` и без ротации разрастается до сотен гигабайт — ограничения в `daemon.json` (см. 4.6) обязательны в проде.

**Сборка: кеш и BuildKit.**

```bash
docker build --no-cache -t myapp:1.0 .      # полностью без кеша (отладка Dockerfile)
docker build --pull -t myapp:1.0 .          # всегда обновить базовый образ
docker build --target builder -t myapp:build .   # собрать только указанный этап multi-stage
docker build --progress=plain -t myapp .    # подробный вывод — видно, какие слои из кеша
```

**Тонкость кеша**: слой кешируется, пока не изменится сама инструкция и все предыдущие слои. `COPY . .` рано в Dockerfile обнуляет кеш всего, что ниже, — поэтому зависимости копируют отдельным слоем раньше кода. Случайный кеш-промах лечится `--no-cache` и правкой порядка инструкций.

**Секреты при сборке (BuildKit)** — в отличие от `ARG` (видны в `docker history`!), секреты через mount не попадают в слои образа:

```dockerfile
# syntax=docker/dockerfile:1
RUN --mount=type=secret,id=pipconf \
    pip install --index-url "$(cat /run/secrets/pipconf)" -r requirements.txt
```

```bash
docker build --secret id=pipconf,src=./pip.conf -t myapp .
```

**Кеш между сборками/машинами** (актуально для CI):

```dockerfile
# Кеш-точка внутри сборки (pip, npm, maven)
RUN --mount=type=cache,target=/root/.cache/pip pip install -r requirements.txt
```

```bash
# Инлайн-кеш: предыдущая сборка хранит метаданные кеша в registry
docker build --build-arg BUILDKIT_INLINE_CACHE=1 --cache-from myapp:latest -t myapp:new .
```

**Управление образами и диском:**

```bash
docker tag myapp:1.0 registry.local:5000/myapp:1.0    # ещё один тег на тот же образ (дедупликация по слоям)
docker history myapp:1.0                              # слои образа — проверка на утечку секретов!
docker save myapp:1.0 | gzip > myapp.tar.gz           # экспорт образа в файл (перенос без registry)
docker load < myapp.tar.gz                            # импорт образа
docker export web | gzip > web-fs.tar.gz              # ФАЙЛОВАЯ СИСТЕМА контейнера (не образ!) → import
docker system df                                      # сколько съели образы/контейнеры/тома
docker system prune -a --filter "until=168h"          # чистка старше недели (-a — и неиспользуемые образы)
docker image prune -a --filter "label!=keep=true"     # чистка по меткам
```

**Сетевые драйверы:**

| Драйвер | Где применяется |
|---|---|
| `bridge` (по умолчанию) | Изолированная сеть; общение по IP; **DNS по имени — только в пользовательском bridge** |
| `host` | Без сетевой изоляции (порты хоста напрямую); быстрее, но менее безопасно |
| `none` | Полная изоляция — ни одного сетевого интерфейса |
| `overlay` | Многохостовые сети (Docker Swarm) |
| `macvlan` | Контейнер получает MAC/IP из локальной физической сети (старые legacy-сервисы) |

```bash
docker network create --driver bridge --subnet 172.28.0.0/16 appnet
docker run -d --network appnet --network-alias db postgres:16   # alias = DNS-имя внутри сети
docker run -d --network appnet -e DB_HOST=db myapp              # резолвится по alias
docker run -d --network container:db myapp                      # шарить сетевой стек ДРУГОГО контейнера
```

**Ограничение ресурсов контейнера:**

```bash
docker run -d --memory 512m --memory-swap 512m --cpus 1.5 --pids-limit 200 nginx
# --memory-swap равен --memory → swap фактически отключён
# Превышение лимита памяти → ядро убивает процесс (OOM), контейнер падает с кодом 137
# Превышение лимита CPU → просто троттлинг, без убийства
```

## Модуль 5. Инфраструктура как код. Docker Compose

### 5.1. Инфраструктура как код (IaC)

**IaC** — подход, при котором инфраструктура (серверы, сети, контейнеры, настройки) описывается в файлах-коде, которые версионируются в Git, проходят ревью и применяются автоматически.

Зачем: **воспроизводимость** (один и тот же файл поднимает окружение где угодно), **удалённость ручных правок** (никаких «зашёл по SSH и поправил конфиг»), **история изменений**, **быстрое восстановление после сбоя**.

Docker Compose — IaC-инструмент для локального и тестового уровня: вся среда приложения описана в YAML-файле.

### 5.2. Оркестрация контейнеров

**Оркестрация** — автоматическое управление жизненным циклом контейнеров: запуск, остановка, перезапуск при падении, масштабирование, сетевое взаимодействие, распределение по хостам.

- **Docker Compose** — оркестрация на одном хосте (для разработки, тестов, небольших систем).
- **Kubernetes** — оркестрация в кластере из множества хостов (продакшен, модуль 8–10).

### 5.3. Секции файла проекта Docker Compose

Файл по умолчанию — **`docker-compose.yml`**. Топ-уровневые секции: `services`, `networks`, `volumes`, `configs`, `secrets`, `profiles` не существует на топ-уровне — профили задаются внутри сервисов.

Полный рабочий пример приложения с БД, кешем, прокси и инициализацией — копипастить целиком и изучать по комментариям:

```yaml
# Имя проекта: контейнеры получат имена <project>-<service>-1
# Версия спецификации указывается ключом "version" в старых релизах;
# в современном Compose (плагин V2) секция version не нужна.

services:
  # ---------- Веб-приложение ----------
  app:
    build:                     # либо build (сборка из Dockerfile)…
      context: .               # контекст сборки — текущая директория
      dockerfile: Dockerfile   # можно явно указать имя Dockerfile
      args:
        - VERSION=1.0.0        # аргументы сборки (ARG в Dockerfile)
    # image: myapp:1.0         # …либо image: использовать готовый образ
    container_name: app        # фиксированное имя контейнера (необязательно)
    restart: unless-stopped    # политика перезапуска: no | always | on-failure | unless-stopped
    ports:
      - "8080:8000"            # публикация: порт_хоста:порт_контейнера
    environment:               # переменные окружения в контейнере
      - DB_HOST=db             # сервисы резолвятся по имени сервиса!
      - DB_USER=${DB_USER:-admin}    # значение по умолчанию, если переменная не задана
      - DB_PASSWORD_FILE=/run/secrets/db_password  # секрет подключается как файл
    env_file:                  # подгрузка переменных из файла
      - .env
    depends_on:                # порядок старта (НЕ ждёт готовности! см. healthcheck)
      db:
        condition: service_healthy
      redis:
        condition: service_started
    networks:
      - frontend
      - backend
    volumes:                   # анонимный том для данных, которые не должны теряться
      - app-data:/data
    secrets:                   # подключение секрета (файл появится в /run/secrets/)
      - db_password
    healthcheck:               # проверка живости — depends_on может ждать service_healthy
      test: ["CMD", "curl", "-f", "http://localhost:8000/health"]
      interval: 30s            # как часто проверять
      timeout: 5s              # сколько ждать ответа
      retries: 3               # сколько неудач подряд = unhealthy
      start_period: 15s        # пауза при старте до начала проверок
    logging:                   # ограничение логов
      driver: "json-file"
      options:
        max-size: "10m"
        max-file: "3"

  # ---------- База данных PostgreSQL ----------
  db:
    image: postgres:16-alpine  # готовый образ; приоритет над build
    restart: always
    environment:
      POSTGRES_USER: ${DB_USER:-admin}
      POSTGRES_PASSWORD: /run/secrets/db_password  # postgres поддерживает *_FILE
      POSTGRES_DB: appdb
    volumes:
      - db-data:/var/lib/postgresql/data   # именованный том — данные переживают пересоздание
    networks:
      - backend          # НЕ выходит во frontend: минимизация доступности
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $${POSTGRES_USER} -d appdb"]
      interval: 10s
      timeout: 5s
      retries: 5

  # ---------- Кеш Redis ----------
  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes", "--maxmemory", "128mb"]
    volumes:
      - redis-data:/data
    networks:
      - backend

  # ---------- Обратный прокси Nginx ----------
  nginx:
    image: nginx:1.27-alpine
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./nginx/nginx.conf:/etc/nginx/nginx.conf:ro   # конфиг с хоста, read-only
      - ./nginx/certs:/etc/nginx/certs:ro
    depends_on:
      - app
    networks:
      - frontend

  # ---------- Одноразовая миграция БД ----------
  migrate:
    build: .
    command: ["python", "manage.py", "migrate"]  # переопределяем CMD Dockerfile
    depends_on:
      db:
        condition: service_healthy
    networks:
      - backend
    profiles: ["migrate"]     # стартует только при явном указании профиля

# ---------- Сети ----------
networks:
  frontend:                    # сеть «снаружи»: nginx <-> app
    driver: bridge
  backend:                     # сеть «внутри»: app <-> db, redis
    driver: bridge

# ---------- Именованные тома ----------
volumes:
  app-data:
  db-data:
  redis-data:

# ---------- Секреты ----------
secrets:
  db_password:
    file: ./secrets/db_password.txt   # секрет читается с хоста, НЕ попадает в репозиторий
```

> Полный файл примера — `examples/05-compose/docker-compose.yml` в репозитории курса.

### 5.4. Использование Docker Compose

```bash
# Поднять всё в фоне (-d) и пересобрать при необходимости (--build)
docker compose up -d --build

# Посмотреть статус сервисов
docker compose ps

# Логи одного сервиса с отслеживанием
docker compose logs -f app

# Выполнить команду в сервисе (миграции, консоль Django и т.п.)
docker compose exec app python manage.py migrate
docker compose exec db psql -U admin -d appdb

# Перезапуск / остановка одного сервиса
docker compose restart app
docker compose stop app && docker compose rm -f app

# Применить изменения файла compose без полного пересоздания
docker compose up -d

# Остановить и удалить контейнеры и сеть (тома остаются)
docker compose down
# Удалить и тома (данные БД пропадут!)
docker compose down -v

# Запуск сервиса с профилем (миграция из примера выше)
docker compose --profile migrate up migrate

# Проверить файл без запуска и вывести итоговую конфигурацию
docker compose config

# Несколько файлов: базовый + оверрайд под среду
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d

# Масштабирование сервиса (при условии, что приложение stateless)
docker compose up -d --scale app=3
```

### 5.5. Особенности Docker Compose

- **Имена**: контейнеры получают имена `<project>-<service>-<num>`, проект — по имени директории (переопределяется флагом `-p` или переменной `COMPOSE_PROJECT_NAME`).
- **DNS**: сервисы резолвят друг друга по имени сервиса внутри общих сетей.
- **`depends_on` управляет порядком, но не готовностью** — для ожидания готовности используйте `condition: service_healthy` + `healthcheck`.
- **Переменные**: `${VAR}` подставляется из окружения хоста или файла `.env` рядом с compose-файлом.
- **Override-файлы**: `docker-compose.yml` (база) + `docker-compose.override.yml` (применяется автоматически) + явные `-f` файлы для сред.
- **Профили**: сервисы с `profiles` не стартуют по умолчанию — полезно для отладочных и one-shot сервисов.

### 5.6. Хорошая практика

1. **Один сервис — одна ответственность**, как в микросервисах.
2. **Секреты только через механизм `secrets` или переменные окружения**, никогда не писать в файл под контролем версий.
3. **Разделение сетей**: БД не должна быть доступна с хоста и из «внешней» сети.
4. **Тома для всех данных**, которые нельзя терять; `down -v` осознанно.
5. **healthcheck для каждого критичного сервиса**.
6. **Один compose-файл на среду** (dev / staging / prod override), общая база без дублирования.
7. Фиксировать **версии образов** тегами (`postgres:16-alpine`, не `postgres:latest`).

### 5.7. Тонкости Docker Compose

**Приоритет переменных окружения** (сверху вниз — более приоритетные):
1. Переменные, уже заданные в shell (`export FOO=bar`).
2. Файл из `--env-file`.
3. `.env` рядом с compose-файлом (подхватывается автоматически).

```bash
# Жёсткие формы подстановки в compose-файле:
#   ${VAR:?сообщение}  — остановить, если VAR не задан (защита от дыр в конфигурации)
#   ${VAR:-default}    — значение по умолчанию
#   ${VAR:+default}    — использовать default, только если VAR задан
docker compose config                    # итоговая конфигурация с подставленными значениями
docker compose --env-file .env.staging config -q   # проверить файл под конкретную среду
```

**`up`, `run`, `exec` — три разных способа «войти», не путать:**

```bash
docker compose up -d app                        # создать/пересоздать и запустить сервис (+ зависимости)
docker compose up -d --no-deps app              # не трогать зависимости
docker compose up -d --build --force-recreate app   # пересобрать образ и пересоздать контейнер принудительно
docker compose run --rm app python manage.py migrate  # РАЗОВЫЙ запуск: новый контейнер поверх сети проекта
docker compose run --rm --no-deps --entrypoint sh app # без зависимостей, с заменой entrypoint
docker compose exec app sh                      # команда в УЖЕ работающем контейнере (как docker exec)
```

**Остальные команды с деталями:**

```bash
docker compose ps --status running              # фильтр по статусу
docker compose logs -f --tail=200 --since 10m app
docker compose top                              # процессы внутри контейнеров сервисов
docker compose events                           # события (старт/стоп/убийство) в реальном времени
docker compose port app 8000                    # какой порт хоста соответствует порту сервиса
docker compose cp app:/app/log.txt ./           # копирование между контейнером и хостом
docker compose build --pull --no-cache          # пересобрать образы всех сервисов с build:
docker compose down --rmi local --remove-orphans    # удалить и собранные локально образы
docker compose kill app && docker compose start app # мгновенный SIGKILL (без grace-period) + старт
```

**Тонкость `depends_on` — повторно и важно:** условие `service_healthy` требует `healthcheck` именно в compose-файле. `HEALTHCHECK` из Dockerfile для условия **не учитывается** — добавляйте явную секцию `healthcheck` у сервиса.

**Секция `deploy`** (из спецификации Swarm) в обычном Compose работает ограниченно: `resources.limits` (квоты CPU/памяти через cgroup) применяются, а `replicas`, `restart_policy`, `placement` — **только в режиме Swarm** (`docker stack deploy`). Не ожидайте реплик от обычного `docker compose up`.

**Изоляция нескольких стендов одним файлом — имя проекта:**

```bash
docker compose -p dev up -d        # контейнеры dev-db-1, dev-app-1…
docker compose -p demo up -d       # рядом живёт второй изолированный стенд demo-db-1…
docker compose -p dev down         # удаляется только «dev»
```

В CI имя проекта по умолчанию берётся из имени директории — параллельные job'ы могут конфликтовать. Фиксируйте: `-p "$CI_PROJECT_PATH_SLUG-$CI_COMMIT_SHORT_SHA"` или `COMPOSE_PROJECT_NAME` в переменных.

**`container_name` ломает масштабирование**: имя уникально, и `up --scale app=3` упадёт с конфликтом имён. В переиспользуемых стендах — без него.

**Healthcheck в compose полностью переопределяет** `HEALTHCHECK` образа: чтобы дополнить параметры образа, подсмотрите их — `docker inspect <image> --format '{{json .Config.Healthcheck}}'` — и перечислите вместе со своими.

## Модуль 6. GitLab и автоматизация

### 6.1. CI/CD

**CI/CD** — практика автоматизации пути кода от коммита до пользователя.

- **Continuous Integration**: каждый коммит автоматически собирается и проходит тесты. Обнаружение поломок — в день их создания.
- **Continuous Delivery**: после CI пакет готов к развёртыванию, но финальный шаг запускается вручную (кнопка).
- **Continuous Deployment**: развёртывание тоже автоматическое, без человека.

### 6.2. Конвейер CI/CD

**Конвейер (pipeline)** состоит из этапов (**stages**), этапы — из заданий (**jobs**). Задание — самостоятельная единица работы (собрать, протестировать, запушить образ), выполняющаяся внутри исполнителя (runner). Задания одного этапа выполняются параллельно, этапы — последовательно: тесты не стартуют, пока не завершена сборка.

Классические этапы: **build → test → security → deploy** (подробно в модуле 7).

### 6.3. Конвейер CI/CD в реальной жизни

Типичный цикл изменения: разработчик пушит ветку `feature/login` → GitLab запускает pipeline ветки (линтеры, юнит-тесты, сборка образа) → создаётся Merge Request → review → после слияния в `main` pipeline собирает релизный образ, прогоняет полный набор проверок и выкатывает на стейджинг; прод — через кнопку или автоматически с ручным подтверждением (manual job).

**Quality Gate**: переход между этапами возможен только при «зелёном» статусе предыдущего — упавший тест блокирует движение дальше.

### 6.4. Системы, реализующие CI/CD

Популярные системы: **GitLab CI/CD** (встроен в GitLab — единая точка: код, ревью, пайплайны, реестр образов), **Jenkins** (классика, гибкость за счёт плагинов), **GitHub Actions**, **CircleCI**, **TeamCity**, **ArgoCD** (непрерывное развёртывание в Kubernetes).

Выбор GitLab обоснован тем, что **репозиторий, CI, container registry и управление релизами живут в одном продукте**.

### 6.5. Что такое GitLab

**GitLab** — веб-платформа для управления жизненным циклом DevOps: Git-репозитории с защищёнными ветками и ревью (Merge Requests), встроенный CI/CD, **Container Registry**, управление задачами (issues), wiki, пакетные реестры, мониторинг. Есть облачная версия (gitlab.com) и self-hosted редакции — CE (Community, бесплатная) и EE (Enterprise).

Компоненты сервера: **GitLab (Rails-приложение)**, **PostgreSQL** (данные), **Redis** (кеш/очереди), **Gitaly** (служба доступа к git-репозиториям), **NGINX** (прокси).

### 6.6. Возможности GitLab (важные для курса)

- **Merge Requests**: ветки, ревью, обсуждения, approval rules.
- **Pipelines**: `.gitlab-ci.yml`, этапы, артефакты, кеш, окружения, переменные (в т.ч. защищённые и masked).
- **Container Registry**: образы по адресу `registry.gitlab.example.com/<group>/<project>` — используется в модулях 7 и 8–10.
- **Runners**: исполнители заданий (см. 6.8–6.9).
- **Environments + Deployments**: отслеживание, что и куда развёрнуто, возможность отката.
- **Schedules**: запуск пайплайнов по расписанию (ночные прогоны, бэкапы).
- **Variables**: `Settings → CI/CD → Variables` — секреты и настройки, не хранящиеся в репозитории.

### 6.7. GitLab CI/CD: инструкция по применению

Пайплайн описывается в файле **`.gitlab-ci.yml`** в корне репозитория. Минимальный рабочий пример и шпаргалка ключевых слов:

```yaml
# ---------- Уровень 1: глобальные настройки ----------
stages:                       # порядок этапов конвейера
  - build
  - test
  - deploy

default:                      # умолчания для всех заданий
  image: alpine:3.20          # образ, внутри которого выполняются скрипты
  before_script:              # выполняется ПЕРЕД script каждого job
    - echo "Job started at $(date)"

variables:                    # переменные пайплайна
  APP_NAME: "myapp"
  DOCKER_IMAGE: "$CI_REGISTRY_IMAGE/myapp"   # CI_REGISTRY_IMAGE — адрес реестра проекта

# ---------- Уровень 2: задания ----------
build-job:
  stage: build
  script:                     # команды задания
    - echo "Собираем артефакты для $APP_NAME"
    - mkdir -p dist
    - echo "build artifact v$CI_COMMIT_SHORT_SHA" > dist/app.txt
  artifacts:                  # файлы, передающиеся между заданиями
    paths:
      - dist/
    expire_in: 1 week         # срок хранения артефактов

lint-job:
  stage: test
  script:
    - echo "Линтеры кода"
  allow_failure: true         # не ронять пайплайн при падении

unit-tests:
  stage: test
  script:
    - test -f dist/app.txt && echo "Артефакт получен"
    - echo "Запуск юнит-тестов"

deploy-staging:
  stage: deploy
  environment:                # окружение в интерфейсе GitLab
    name: staging
    url: https://staging.example.com
  script:
    - echo "Деплой на стейджинг версии $CI_COMMIT_SHORT_SHA"
  rules:                      # условия создания задания
    - if: $CI_COMMIT_BRANCH == "main"      # только ветка main

deploy-production:
  stage: deploy
  environment:
    name: production
    url: https://example.com
  script:
    - echo "Деплой в продакшен"
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
      when: manual            # ручной запуск из интерфейса (кнопка ▶)
```

Ключевые предопределённые переменные: `$CI_COMMIT_SHA`, `$CI_COMMIT_SHORT_SHA`, `$CI_COMMIT_BRANCH`, `$CI_PIPELINE_IID`, `$CI_REGISTRY`, `$CI_REGISTRY_IMAGE`, `$CI_REGISTRY_USER`, `$CI_REGISTRY_PASSWORD`, `$CI_PROJECT_DIR`.

Частые ключи заданий:

| Ключ | Назначение |
|---|---|
| `image` | Образ контейнера, в котором выполняется job (для docker executor) |
| `services` | Вспомогательные контейнеры рядом с job (например, `docker:dind` для сборки образов) |
| `script` | Команды задания (обязательно) |
| `stage` | Этап задания |
| `needs` | Зависимость от конкретного job вместо всей стадии (ускоряет, создаёт DAG) |
| `dependencies` | От каких job брать артефакты |
| `artifacts` / `cache` | Артефакты — результаты; кеш — ускорение повторных сборок |
| `rules` / `only` / `except` | Условия выполнения (rules — современный синтаксис) |
| `when` | `on_success`, `on_failure`, `always`, `manual`, `never` |
| `environment` | Окружение развёртывания (стейджинг/прод) |
| `before_script` / `after_script` | Обвязка вокруг `script` |

```yaml
# Типовые правила: MR-пайплайны для веток, полный пайплайн для main
workflow:
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH == "main"

# Кеш для ускорения: node_modules / pip / maven между пайплайнами
unit-tests:
  stage: test
  cache:
    key: "$CI_COMMIT_REF_SLUG"        # отдельный кеш на ветку
    paths:
      - .cache/pip
  script:
    - pip install --cache-dir .cache/pip -r requirements.txt
    - pytest
```

### 6.8. GitLab Runner

**GitLab Runner** — агент, который берёт задания у GitLab-сервера и выполняет их. Типы:

- **Shared Runner** — общий для всего GitLab.
- **Group Runner** — общий для группы проектов.
- **Specific (Project) Runner** — привязан к одному проекту, только он может выполнять его задания.

**Теги (tags)**: задание выполнится на раннере, у которого есть все теги из списка `tags:` — механизм маршрутизации (например, `docker`, `prod`, `gpu`).

**Исполнители (executors)** — среда запуска заданий:

| Executor | Описание | Когда применять |
|---|---|---|
| `shell` | Команды выполняются прямо в ОС раннера | Простые задачи на выделенном хосте |
| `docker` | Каждое задание — в контейнере из `image:` (чистота, изоляция) | **Основной выбор** |
| `docker+machine` / autoscale | Автоматическое создание машин под нагрузку | Облако, переменчивые очереди |
| `kubernetes` | Job запускается как pod в кластере | Крупные инсталляции |
| `ssh` | Удалённый запуск по SSH | Легаси-хосты |

### 6.9. Настройка GitLab Runner

Установка и регистрация раннера (Linux):

```bash
# 1. Установка (Debian/Ubuntu; для других ОС — официальный скрипт/пакеты)
curl -L "https://packages.gitlab.com/install/repositories/runner/gitlab-runner/script.deb.sh" | sudo bash
sudo apt install gitlab-runner
sudo systemctl enable --now gitlab-runner

# 2. Регистрация: токен берётся в GitLab → Settings → CI/CD → Runners → New project runner
sudo gitlab-runner register \
  --non-interactive \
  --url "https://gitlab.example.com/" \
  --token "glrt-xxxxxxxxxxxx" \        # токен проекта (authentication token)
  --executor "docker" \
  --docker-image "alpine:3.20" \       # образ по умолчанию, если job не указал image
  --docker-privileged \                # нужно, если планируется dind-сборка образов
  --tag-list "docker,linux" \
  --description "docker-runner-01"

# 3. Проверка
sudo gitlab-runner list
sudo gitlab-runner status
sudo gitlab-runner verify
```

Итог регистрации — файл **`/etc/gitlab-runner/config.toml`** (ручная доводка параметров):

```toml
concurrent = 4                      # сколько job одновременно может исполнять раннер

[[runners]]
  name = "docker-runner-01"
  url = "https://gitlab.example.com/"
  token = "glrt-xxxxxxxxxxxx"
  executor = "docker"
  limit = 4
  [runners.docker]
    tls_verify = false
    image = "alpine:3.20"           # образ по умолчанию
    privileged = true               # требуется для docker:dind (сборка образов в job)
    disable_cache = false
    volumes = ["/cache", "/var/run/docker.sock:/var/run/docker.sock"]
    # Соккер докера: альтернатива dind — сборка образов на демоне хоста (быстрее, но менее изолировано)
    shm_size = 0
  [runners.cache]
    Type = "s3"                     # распределённый кеш для нескольких раннеров
```

После правки: `sudo gitlab-runner restart`. Управление: `sudo gitlab-runner start|stop|restart`, логи — `journalctl -u gitlab-runner -f`.

### 6.10. Сценарий автоматизации

Сквозной пример: репозиторий приложения + раннер с docker executor. Задания: линт и тесты на каждый пуш, сборка и пуш образа в registry GitLab, деплой на стейджинг из `main`, прод — вручную. Задания сборки образа используют образ `docker` с сервисом `docker:dind` (Docker-in-Docker) — внутри job поднимается независимый демон Docker.

```yaml
# .gitlab-ci.yml — сценарий автоматизации проекта
stages:
  - validate
  - build
  - deploy

# Задания проверки кода: сработают на любой пуш и в MR
lint:
  stage: validate
  image: python:3.12-slim
  script:
    - pip install ruff
    - ruff check .

unit-tests:
  stage: validate
  image: python:3.12-slim
  cache:
    key: pip-cache
    paths:
      - .pip-cache
  script:
    - pip install --cache-dir .pip-cache -r requirements.txt
    - pytest -v --junitxml=report.xml
  artifacts:
    when: always                     # сохранять отчёт даже при падении тестов
    reports:
      junit: report.xml              # тесты отобразятся в интерфейсе MR

# Сборка и публикация образа
build-image:
  stage: build
  image: docker:27                  # клиент Docker
  services:
    - docker:27-dind                # сервис с демоном Docker (Docker-in-Docker)
  variables:
    DOCKER_TLS_CERTDIR: "/certs"    # TLS между клиентом и dind
    IMAGE_TAG: "$CI_REGISTRY_IMAGE/myapp:$CI_COMMIT_SHORT_SHA"
  script:
    - echo "$CI_REGISTRY_PASSWORD" | docker login -u "$CI_REGISTRY_USER" "$CI_REGISTRY" --password-stdin
    - docker build -t "$IMAGE_TAG" .
    - docker tag "$IMAGE_TAG" "$CI_REGISTRY_IMAGE/myapp:latest"
    - docker push "$IMAGE_TAG"
    - docker push "$CI_REGISTRY_IMAGE/myapp:latest"
  rules:
    - if: $CI_COMMIT_BRANCH == "main"          # образ версионируется только с main

# Деплой через SSH на целевой хост
deploy-staging:
  stage: deploy
  image: alpine:3.20
  before_script:
    - apk add --no-cache openssh-client
    - eval $(ssh-agent -s)
    - echo "$STAGING_SSH_PRIVATE_KEY" | tr -d '\r' | ssh-add -   # секрет из CI/CD Variables
    - mkdir -p ~/.ssh && ssh-keyscan staging.example.com >> ~/.ssh/known_hosts
  script:
    # Пул свежего образа на хосте и перезапуск контейнера
    - ssh deploy@staging.example.com "docker login -u $CI_REGISTRY_USER -p $CI_REGISTRY_PASSWORD $CI_REGISTRY
      && docker pull $CI_REGISTRY_IMAGE/myapp:latest
      && docker stop myapp || true
      && docker rm myapp || true
      && docker run -d --name myapp --restart always -p 80:8000 $CI_REGISTRY_IMAGE/myapp:latest"
  environment:
    name: staging
    url: https://staging.example.com
  rules:
    - if: $CI_COMMIT_BRANCH == "main"

deploy-production:
  stage: deploy
  image: alpine:3.20
  script:
    - echo "Аналогичный деплой на продакшен-хост"
  environment:
    name: production
    url: https://example.com
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
      when: manual                 # развёртывание в прод только по кнопке
  allow_failure: false
```

Перед запуском в GitLab (Settings → CI/CD → Variables) создайте:

> Полный сценарий — `examples/06-07-gitlab-ci/.gitlab-ci.yml` в репозитории курса.
- `STAGING_SSH_PRIVATE_KEY` — тип File или masked, защищённая переменная;
- при необходимости `CI_REGISTRY_USER/PASSWORD` уже предопределены.

### 6.11. Углублённый разбор: ключевые слова и тонкости GitLab CI/CD

**Источники пайплайна (`$CI_PIPELINE_SOURCE`)**: `push` (по умолчанию), `merge_request_event`, `schedule` (по расписанию), `web` (кнопка «Run pipeline»), `api`, `trigger` (из другого пайплайна), `pipeline` (child/downstream), `external`. Источник — первое, на что смотрят `rules`:

```yaml
workflow:
  rules:
    # Полный пайплайн для main; проверочный для MR; пуши в прочие ветки — не запускаем
    - if: $CI_COMMIT_BRANCH == "main"
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - when: never
```

**Merge Request пайплайны**: при `$CI_PIPELINE_SOURCE == "merge_request_event"` GitLab собирает пайплайн в отдельном контексте («detached»): `CI_COMMIT_REF_SLUG` содержит `mr-N`, а исходная ветка доступна как `$CI_MERGE_REQUEST_SOURCE_BRANCH_NAME`. Так проверки в MR отличаются от сборки ветки.

**`needs` — DAG вместо стадий:** задание стартует сразу после завершения перечисленных job, минуя ожидание всей стадии:

```yaml
deploy-staging:
  needs:
    - job: build-image
      artifacts: true         # забрать артефакты именно отсюда
    - job: trivy-scan
      artifacts: false        # ждать только статуса
    # - job: optional-job
    #   optional: true        # не падать, если задание выключено правилами
```

**Кеш vs артефакты — в чём разница:**
- **artifacts** — результат сборки: передаётся между job, скачивается через UI, имеет срок жизни и типы отчётов;
- **cache** — только ускорение (зависимости): **не гарантирован** между раннерами, отчётности нет.

```yaml
job:
  cache:
    key:
      files:                 # кеш сбрасывается при изменении перечисленных файлов
        - package-lock.json
    paths:
      - node_modules/
    policy: pull-push        # по умолчанию; «только тянуть» — pull, «только писать» — push
```

**Отчёты в артефактах:**

```yaml
  artifacts:
    when: always
    reports:
      junit: report.xml              # отображаются на вкладке Tests и в MR
      dotenv: build.env              # экспорт переменных в СЛЕДУЮЩИЕ задания (механизм передачи IMAGE:TAG)
      coverage_report:
        coverage_format: cobertura
        path: coverage.xml
  coverage: '/TOTAL.*?(\d+(?:\.\d+)?)%/'   # регулярка для процента покрытия
```

**Окружения подробнее** — `on_stop` (job-«уборщик» при остановке среды — основа Review Apps), `auto_stop_in` (автоостановка), `deployment_tier`, `action`:

```yaml
review:
  stage: deploy
  environment:
    name: review/$CI_COMMIT_REF_SLUG
    url: https://$CI_ENVIRONMENT_SLUG.review.example.com
    on_stop: stop_review
    auto_stop_in: 2 days
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"

stop_review:
  stage: deploy
  script:
    - ./delete_review_env.sh "$CI_ENVIRONMENT_SLUG"
  environment:
    name: review/$CI_COMMIT_REF_SLUG
    action: stop
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
      when: manual
```

**Композиция конфигурации — `include` и шаблоны:**

```yaml
include:
  - local: '/ci/build.yml'                       # файл в этом репозитории
  - project: 'devops/ci-templates'               # из другого проекта GitLab
    ref: v1.2.0
    file: '/docker-build.yml'
  - template: Jobs/SAST.gitlab-ci.yml            # встроенные шаблоны GitLab
  - remote: 'https://example.com/remote-ci.yml'  # по URL

# «Скрытые» job'ы (точка в начале имени) — переиспользуются через extends
.docker:
  image: docker:27
  services: [docker:27-dind]

build:
  extends: .docker
  script: [docker build -t app .]
```

**Переменные: приоритет и защита.** От менее приоритетных к более: автоматические → `variables` верхнего уровня → project/group Settings → переменные ручного запуска пайплайна → job-уровень. **Protected variables** видны только job'ам на защищённых ветках/тегах (`main`, релизы) — **секреты прода держите именно так**. **Masked** скрывает значение в логах (требования: без переводов строк, длина ≥ 8). Тонкость деплоев по SSH: `$VAR` внутри `script` раскрывает GitLab на раннере, а `'$VAR'` внутри строки ssh — shell уже на удалённом хосте: пишите осознанно.

**Параллелизм и матрицы:**

```yaml
test:
  parallel:
    matrix:                      # job на каждую комбинацию: test: [pg14/pg15/pg16, node20]
      - PG_VERSION: ["14", "15", "16"]
        NODE_VERSION: ["20"]
  script:
    - echo "Прогон против Postgres $PG_VERSION, Node $NODE_VERSION"
```

**Надёжность заданий:** `retry: {max: 2, when: [runner_system_failure, stuck_or_timeout_failure]}` — повторять только на инфраструктурных сбоях, не маскируя реальные ошибки; `timeout: 30 minutes` на job; `interruptible: true` — отменять job при появлении нового пайплайна на той же ветке (экономит раннеры).

**Runner'ы: детали и ловушки.**

- **Shell executor**: быстро, но хост «пылится» (артефакты, процессы), job'и видят друг друга. Подходит для выделенных агентов (например, деплой-раннеры).
- **Docker executor**: изоляция через контейнер `image:`; образ скачивается на каждый хост — прогревайте раннер (`docker pull` по cron) или держите mirror.
- **Docker-in-Docker (`services: docker:dind`)**: изолированный демон внутри привилегированного контейнера; требует `privileged = true` в `config.toml` раннера (job теоретически может влиять на хост); TLS — через `DOCKER_TLS_CERTDIR: "/certs"`.
- **Вариант «соккер хоста»**: `volumes: ["/var/run/docker.sock:/var/run/docker.sock"]` — сборки быстрее (общий кеш образов), но job получает **root-доступ на хост**; допустимо только на изолированных раннерах без чужих job.
- **Защищённые раннеры** (Protected): берут job только с защищённых веток/тегов — основа разделения «кто может деплоить в прод».
- Флаг **«Run untagged jobs»**: без него раннер не возьмёт job без тегов — частая причина зависших пайплайнов в очереди.

**Дочерние пайплайны (child pipelines) для монорепозиториев:**

```yaml
trigger-backend:
  trigger:
    include: backend/.gitlab-ci.yml
    strategy: depend            # родитель ждёт итоговый статус дочернего
  rules:
    - changes:
        - backend/**/*           # запускаем, только если менялось в backend/
```

**Отладка пайплайнов:** кнопка **«Run pipeline»** (ручной запуск с подстановкой переменных), **CI Lint** (Validate в редакторе файла), просмотр вычисленных переменных на странице job'а, job-диагност с `env | grep CI_ | sort`, `when: always` для заданий-свидетелей, web terminal к job'у (если раннер поддерживает).

### 6.12. Установка GitLab через Docker Compose

GitLab поставляется как монолитный образ **Omnibus** (`gitlab-ce` — Community, `gitlab-ee` — Enterprise): один контейнер содержит веб, Git, CI, registry. Поднимаем его вместе с раннером одним compose-файлом.

```yaml
# docker-compose.yml — GitLab CE + раннер
services:
  gitlab:
    image: gitlab/gitlab-ce:17.6.1-ce.0   # фиксируйте версию, а не latest
    hostname: gitlab.example.com          # имя для URL и ссылок в письмах
    restart: always
    environment:
      # Вся настройка Omnibus — одной строкой Ruby-конфига:
      GITLAB_OMNIBUS_CONFIG: |
        external_url 'http://gitlab.example.com'      # для HTTPS: 'https://…' + настройка сертификатов
        gitlab_rails['gitlab_shell_ssh_port'] = 2222  # git clone по SSH будет на порту хоста 2222
        gitlab_rails['initial_root_password'] = 'ChangeMe!123'  # только для стенда; потом сменить
        # Ограничения для слабой машины (GitLab просит минимум 4 ГБ RAM):
        puma['worker_processes'] = 2
        sidekiq['max_concurrency'] = 10
        prometheus_monitoring['enable'] = false
        registry['enable'] = true          # встроенный Container Registry (нужен в модулях 7 и 8–10)
    ports:
      - "80:80"        # HTTP → external_url
      - "443:443"      # HTTPS (пока не настроен — не используется)
      - "2222:22"      # git over SSH
    volumes:
      - gitlab-config:/etc/gitlab          # gitlab.rb, SSL, secrets
      - gitlab-logs:/var/log/gitlab
      - gitlab-data:/var/opt/gitlab        # репозитории, БД, артефакты, registry
    shm_size: '256m'                        # иначе вылетают воркеры при больших репозиториях

  gitlab-runner:
    image: gitlab/gitlab-runner:alpine-v17.6.1   # major-версия раннера ≈ major-версии GitLab
    restart: always
    depends_on:
      - gitlab
    volumes:
      - runner-config:/etc/gitlab-runner            # config.toml раннера
      - /var/run/docker.sock:/var/run/docker.sock   # раннер запускает job-контейнеры на демоне хоста

volumes:
  gitlab-config:
  gitlab-logs:
  gitlab-data:
  runner-config:
```

> Файл стека — `examples/06-07-gitlab-ci/gitlab-docker-compose.yml` в репозитории курса.

Развёртывание и первичная настройка:

```bash
docker compose up -d
# Первая инициализация занимает 3–10 минут — следим:
docker compose logs -f gitlab
# Если пароль не задали в GITLAB_OMNIBUS_CONFIG:
docker compose exec gitlab cat /etc/gitlab/initial_root_password
# Вход: http://gitlab.example.com → root / <пароль>

# Регистрация раннера (токен: GitLab → Admin Area → CI/CD → Runners):
docker compose exec gitlab-runner gitlab-runner register --non-interactive \
  --url "http://gitlab/" \                     # внутри сети compose — имя сервиса
  --token "glrt-xxxxxxxxxxxx" \
  --executor "docker" \
  --docker-image "alpine:3.20" \
  --docker-privileged \                        # нужно для docker:dind job'ов
  --tag-list "docker,dind" \
  --description "compose-runner-01"

docker compose exec gitlab-runner gitlab-runner verify
docker compose restart gitlab-runner           # применить config.toml
```

**Тонкости:** GitLab требует **минимум 4 ГБ RAM** (иначе регулярные OOM); хранилище `/var/opt/gitlab` быстро растёт — registry и артефакты чистите политиками (модуль 7); адрес клонирования важен: при неверном `external_url` ссылки в UI будут вести не туда; SSH для git в этом стенде — порт **2222**: `git clone ssh://git@gitlab.example.com:2222/group/project.git`.

### 6.13. Раннер: docker executor + Docker-in-Docker (dind)

**Задача:** внутри job'а собирать и пушить Docker-образы (модули 7). Job исполняется в контейнере `docker:27`, а рядом сервис-под контейнером `docker:27-dind` поднимается **полноценный демон Docker** — у каждого job'а свой чистый демон.

Регистрация (см. также 6.9) и `config.toml` раннера:

```toml
[[runners]]
  executor = "docker"
  [runners.docker]
    image = "alpine:3.20"
    privileged = true                 # ОБЯЗАТЕЛЬНО: dind-сервис — привилегированный контейнер
    volumes = ["/cache"]
```

Job, собирающий образ:

```yaml
build-image:
  stage: build
  image: docker:27                    # клиент Docker (образ содержит docker CLI)
  services:
    - docker:27-dind                  # демон Docker как сервис; доступен в job по имени "docker"
  variables:
    DOCKER_TLS_CERTDIR: "/certs"      # TLS между клиентом и dind; сертификаты шарятся через volume
    IMAGE: "$CI_REGISTRY_IMAGE/myapp:$CI_COMMIT_SHORT_SHA"
  before_script:
    # docker:27 сам подхватит сертификаты из /certs и настроит DOCKER_HOST=tcp://docker:2376
    - echo "$CI_REGISTRY_PASSWORD" | docker login -u "$CI_REGISTRY_USER" "$CI_REGISTRY" --password-stdin
  script:
    - docker build -t "$IMAGE" .
    - docker push "$IMAGE"
```

**Тонкости dind:**
- **Без `privileged = true` в config.toml раннера dind не стартует** — job упадёт с «docker: Cannot connect to the Docker daemon».
- Имя сервиса по умолчанию — `docker` (alias = имя образа); можно явно: `services: [{ name: docker:27-dind, alias: dind }]` и тогда `DOCKER_HOST=tcp://dind:2376`.
- `DOCKER_TLS_CERTDIR` нужен для изоляции сертификатов при параллельных job'ах на одном раннере.
- Каждый job получает **чистый демон**: никакого кеша образов между пайплайнами — компенсируем `--cache-from` (модуль 7).
- **Безопасность:** `privileged` даёт dind-котейнеру почти полный доступ к ядру хоста — не используйте такой раннер для ненадёжного кода. Альтернативы без privileged: **kaniko** (`gcr.io/kaniko-project/executor` — сборка в userspace без демона), **buildah**, либо соккер хоста (см. 6.11).

### 6.14. Раннер: shell executor

**Задача:** выполнять job'и прямо в ОС раннера — без контейнерной обёртки. Минимум накладных расходов, прямой доступ к железу (GPU, USB-устройства) и локальным сервисам хоста.

Регистрация и подготовка хоста:

```bash
# Регистрация
sudo gitlab-runner register --non-interactive \
  --url "https://gitlab.example.com/" --token "glrt-xxx" \
  --executor "shell" \
  --tag-list "shell,deploy" \
  --description "shell-runner-01"

# Job'ы выполняет системный пользователь gitlab-runner.
# Для docker-команд на хосте — в группу docker:
sudo usermod -aG docker gitlab-runner

# Каталоги сборок (их задание очистки — на вас, см. ниже)
sudo mkdir -p /home/gitlab-runner/builds /home/gitlab-runner/cache
sudo chown -R gitlab-runner:gitlab-runner /home/gitlab-runner
```

```toml
# /etc/gitlab-runner/config.toml
concurrent = 2                        # параллельные job'и на этом хосте — осознанно!
[[runners]]
  executor = "shell"
  builds_dir = "/home/gitlab-runner/builds"
  cache_dir  = "/home/gitlab-runner/cache"
  shell = "bash"                      # или sh
```

Примеры job'ов на shell-раннере:

```yaml
# Сборка/тесты прямо на хосте: используются установленные там инструменты
build-on-host:
  stage: build
  tags: [shell]
  script:
    - make deps          # make, gcc, библиотеки — всё берётся с хоста
    - make test

# Классика применения: деплой на «соседний» хост по SSH
deploy-production:
  stage: deploy
  tags: [shell, deploy]          # job попадёт ТОЛЬКО на этот раннер
  script:
    - ssh deploy@prod.example.com ./deploy.sh "$CI_COMMIT_SHORT_SHA"
  environment:
    name: production
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
      when: manual
```

**Тонкости shell executor:**
- **Нет изоляции**: job'и видят друг друга и всю ОС; `concurrent > 1` — только если job'и это допускают (иначе порча файлов, гонки за порты). Для недоверенного кода — не подходит.
- **Окружение job'а = окружение хоста**: нужные инструменты устанавливаются на хост заранее (`docker` → группа `docker`, `kubectl` → kubeconfig пользователя `gitlab-runner`, SSH-ключи → `~gitlab-runner/.ssh` с правильными правами `600`).
- **Очистка за собой:** каталог сборок и кеши растут — настройте cron: `find /home/gitlab-runner/builds -mindepth 1 -maxdepth 1 -mtime +7 -exec rm -rf {} +` или `docker system prune` на хосте.
- Артефакты и кеш работают как обычно (кладутся в `cache_dir`).
- Отличный выбор для: деплой-раннеров (доступ к целевым хостам по SSH), сборок с GPU/специфичным железом, быстрых простых задач на доверенной инфраструктуре.

**Сводная таблица исполнителей раннера для типового проекта:**

| | docker executor | dind (сервис) | shell executor |
|---|---|---|---|
| Изоляция job'ов | Контейнер на хосте | + свой демон Docker внутри | Нет |
| Сборка образов | Через dind или соккер | Да, нативно | Если docker на хосте |
| Скорость старта | Средняя (pull образов) | Медленнее (подъём демона) | Мгновенно |
| Права на хост | Ограниченные | privileged — высокие | Полные пользователя gitlab-runner |
| Типовое применение | Линт, тесты, сборки | Build/push образов (CI/CD) | Деплой, GPU, железо, «доверенные» хосты |

## Модуль 7. Docker в CI/CD. Завершение конвейера

### 7.1. Идеальный конвейер

**Идеальный конвейер** — быстрый, надёжный, воспроизводимый: один и тот же образ проходит все проверки и разворачивается на все среды без пересборки (**«build once, deploy everywhere»**). Порядок этапов:

```
commit → build → test → security → deploy (staging → production)
```

Схема: страница «05. Конвейер CI/CD» в `k8s_schemes.drawio`.

Принципы: ранние проверки дешевле поздних (линтеры — секунды, интеграционные — минуты, инцидент в проде — часы); каждый этап — качель ворот (quality gate); артефакты несут тег версии (SHA коммита), а не `latest` в путях к продакшену.

### 7.2. Сборка (build)

Сборка в CI отличается от локальной: нужен чистый контекст (`.dockerignore` обязателен), кеш между пайплайнами и правильная схема тегов.

```yaml
build-image:
  stage: build
  image: docker:27
  services:
    - docker:27-dind
  variables:
    DOCKER_TLS_CERTDIR: "/certs"
    IMAGE: "$CI_REGISTRY_IMAGE/myapp"
    TAG: "$CI_COMMIT_SHORT_SHA"          # неизменяемый тег = трассируемость
  script:
    - echo "$CI_REGISTRY_PASSWORD" | docker login -u "$CI_REGISTRY_USER" "$CI_REGISTRY" --password-stdin
    # Кеш сборки в реестре: повторная сборка перезапускается с закешированных слоёв
    - docker build
      --cache-from "$IMAGE:latest"
      --build-arg VERSION="$CI_COMMIT_SHA"
      -t "$IMAGE:$TAG"
      -t "$IMAGE:latest"
      .
    - docker push "$IMAGE:$TAG"
    - docker push "$IMAGE:latest"
  # Имя образа передаём дальше по пайплайну через dotenv-артефакт
  artifacts:
    reports:
      dotenv: image.env
```

```dockerfile
# Dockerfile приложения (пример к модулю 7)
FROM python:3.12-slim AS base
ENV PYTHONUNBUFFERED=1
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
ARG VERSION=dev
ENV APP_VERSION=$VERSION            # версия зашивается в образ
RUN useradd -m appuser && chown -R appuser /app
USER appuser
EXPOSE 8000
CMD ["python", "app.py"]
```

### 7.3. Тестирование

Идея: тесты запускаются **внутри контейнера или рядом с ним**, чтобы окружение тестов совпадало с продом. Паттерн: job с `docker:dind` поднимает приложение и соседний контейнер с тестами.

```yaml
integration-tests:
  stage: test
  image: docker:27
  services:
    - docker:27-dind
  needs: ["build-image"]               # не ждём всю стадию, только сборку
  script:
    - echo "$CI_REGISTRY_PASSWORD" | docker login -u "$CI_REGISTRY_USER" "$CI_REGISTRY" --password-stdin
    # Поднимаем тестовый стенд: приложение + БД, сеть для них
    - docker network create test-net
    - docker run -d --name db --network test-net -e POSTGRES_PASSWORD=test postgres:16-alpine
    - docker run -d --name app --network test-net -p 8000:8000 "$IMAGE:$TAG"
    - |
      # Ожидаем готовности приложения (простой health-wait)
      for i in $(seq 1 30); do
        if docker exec app wget -q -O /dev/null http://localhost:8000/health; then break; fi
        sleep 2
      done
    # Контейнер-тестировщик в той же сети обращается к сервисам по имени
    - docker run --rm --network test-net
      -e BASE_URL=http://app:8000
      "$CI_REGISTRY_IMAGE/test-runner:latest"
    # Альтернатива: docker compose для стенда (см. модуль 5)
    # - docker compose -f tests/docker-compose.test.yml up --abort-on-container-exit
```

### 7.4. Безопасность

Этап **security** — обязательный quality gate. Два уровня:

1. **Статический анализ Dockerfile** — hadolint ловит плохие практики.
2. **Сканирование образов** — **Trivy** ищет уязвимости (CVE) в пакетах ОС и зависимостях приложения; **Grype** — альтернатива. Порог `CRITICAL` обычно блокирует релиз.

```yaml
lint-dockerfile:
  stage: security
  image: hadolint/hadolint:latest-alpine
  script:
    - hadolint Dockerfile                  # правила: DL*, SC*

trivy-scan:
  stage: security
  image: docker:27
  services:
    - docker:27-dind
  needs: ["build-image"]
  variables:
    DOCKER_TLS_CERTDIR: "/certs"
  script:
    - echo "$CI_REGISTRY_PASSWORD" | docker login -u "$CI_REGISTRY_USER" "$CI_REGISTRY" --password-stdin
    - docker pull "$IMAGE:$TAG"
    - |
      # Сканируем образ; выходной код ненулевой, если есть критические CVE
      docker run --rm -v /var/run/docker.sock:/var/run/docker.sock \
        aquasec/trivy:latest image \
        --severity CRITICAL,HIGH \
        --exit-code 1 \
        --no-progress \
        "$IMAGE:$TAG"
  allow_failure: false        # критические уязвимости блокируют пайплайн
```

Дополнительно: сканирование секретов в репозитории (**gitleaks/trufflehog**), проверка лицензий, **SAST** (Static Application Security Testing), политики подписи образов (Docker Content Trust / cosign).

### 7.5. Развёртывание

Развёртывание контейнера на целевом хосте: pull образа по точному тегу, остановка старого контейнера, запуск нового. Для нулевого простоя применяют rolling-стратегии (blue-green, canary) — в Kubernetes это встроено, на «голом» Docker делается вручную.

```yaml
deploy-staging:
  stage: deploy
  image: alpine:3.20
  needs: ["build-image", "trivy-scan", "integration-tests"]
  before_script:
    - apk add --no-cache openssh-client
    - eval $(ssh-agent -s)
    - echo "$STAGING_SSH_PRIVATE_KEY" | tr -d '\r' | ssh-add -
    - mkdir -p ~/.ssh && ssh-keyscan -H staging.example.com >> ~/.ssh/known_hosts
  script:
    # Каждый шаг завершает пайплайн при ошибке — деплой атомарен
    - ssh deploy@staging.example.com "set -e;
        echo '$CI_REGISTRY_PASSWORD' | docker login -u $CI_REGISTRY_USER --password-stdin $CI_REGISTRY;
        docker pull $IMAGE:$TAG;
        docker stop myapp || true;
        docker rm myapp || true;
        docker run -d --name myapp --restart unless-stopped
          --env-file /opt/myapp/env.list
          -p 80:8000 $IMAGE:$TAG;
        docker image prune -f"
    # Пост-деплойная проверка: хелсчек снаружи
    - apk add --no-cache curl
    - curl -fsS https://staging.example.com/health || (echo "Деплой не прошёл проверку" && exit 1)
  environment:
    name: staging
    url: https://staging.example.com
  rules:
    - if: $CI_COMMIT_BRANCH == "main"

# Прод: та же механика, но ручной запуск + окружение production
deploy-production:
  stage: deploy
  image: alpine:3.20
  script:
    - echo "Аналогично на продакшен-хост(ы)"
  environment:
    name: production
    url: https://example.com
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
      when: manual
  allow_failure: false
```

**Итоговая карта конвейера модуля 7:**

| Этап | Задание | Инструмент | Gate |
|---|---|---|---|
| build | build-image | docker build + push registry | образ собран |
| test | unit-tests, integration-tests | pytest + docker стенд | тесты зелёные |
| security | lint-dockerfile, trivy-scan | hadolint, trivy | нет критических CVE |
| deploy | deploy-staging, deploy-production | ssh + docker run | staging auto, prod manual |

### 7.6. Тонкости: версионирование образов, стратегии деплоя, откат

**Схема тегов — что выбрать:**
- **`<ветка>-<short-sha>`** (например, `main-a1b2c3d`) — полная трассируемость «образ ↔ коммит», иммутабельность;
- **SemVer** (`1.4.2`) — релизные образы по git-тегам: `rules: - if: $CI_COMMIT_TAG`;
- **`latest`** — удобен для локального теста, **не для указания версии в проде**: содержимое меняется, воспроизводимость теряется.

```yaml
build-image:
  script:
    - |
      if [ -n "$CI_COMMIT_TAG" ]; then IMAGE_TAG="$CI_COMMIT_TAG";
      else IMAGE_TAG="$CI_COMMIT_REF_SLUG-$CI_COMMIT_SHORT_SHA"; fi
    - docker build -t "$IMAGE:$IMAGE_TAG" .
    - echo "IMAGE_TAG=$IMAGE_TAG" >> image.env        # → artifacts:reports:dotenv
  artifacts:
    reports:
      dotenv: image.env
```

**Кеш сборки в CI с dind — две рабочие схемы:** pull предыдущего образа + `--cache-from "$IMAGE:latest"` (см. 7.2) либо BuildKit-инлайн-кеш (`--build-arg BUILDKIT_INLINE_CACHE=1` + тот же `--cache-from`). Обе требуют, чтобы registry хранил предыдущую сборку — первый пайплайн соберётся без кеша, это нормально.

**Стратегии развёртывания контейнеров:**

| Стратегия | Как работает | Доступность | Откат |
|---|---|---|---|
| **Recreate** | Остановить всё → запустить новое | Даунтайм | Запуск старого образа |
| **Rolling** (посменно) | Обновляем по одному инстансу; старые и новые живут вместе | Без простоя | Поднять обратно старые инстансы |
| **Blue-Green** | Два одинаковых стенда: «blue» работает, «green» обновляется → переключение балансировщика | 2× ресурсы, общее состояние | Мгновенный: вернуть трафик на blue |
| **Canary** | Малый % трафика на новую версию → наблюдение → наращивание | Нужна управляемая балансировка | Убрать канарейку |

Идея blue-green на одном хосте: приложение за прокси смотрит на `127.0.0.1:8080`; деплой поднимает `myapp:новый` на 8081, гонит smoke-тест, переключает upstream и останавливает старый. Canary полноценно реализуется в Kubernetes (веса Ingress/Service) — см. модули 8–10.

**Smoke-тест после деплоя — минимальный gate:**

```yaml
post-deploy-check:
  stage: deploy
  needs: [deploy-staging]
  image: alpine:3.20
  script:
    - apk add --no-cache curl
    - curl -fsS --retry 10 --retry-delay 5 --retry-all-errors https://staging.example.com/health
    - curl -fsS https://staging.example.com/ | grep -q "My App"
```

**Процедура отката на «голом» Docker:** старые образы сохраняются в registry, поэтому откат = деплой прежнего тега тем же сценарием с `IMAGE_TAG` прошлой версии (список тегов — в интерфейсе registry). В Kubernetes откат тривиален: `kubectl rollout undo` (модуль 8) или `helm rollback` (модуль 10) — ещё один аргумент в пользу оркестратора.

**Поиск секретов в истории коммитов (дополнение к безопасности):**

```yaml
gitleaks:
  stage: security
  image: zricethezav/gitleaks:latest
  script:
    - gitleaks detect --source . --verbose --redact
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
```

**Ротация образов в registry:** включите **Cleanup policy** (Settings → Packages and registries → Cleanup policies) — иначе registry разрастётся; стандарт хранения: «последние N образов на имя».

## Модуль 8. Kubernetes. Инструментарий и основные компоненты

> **Наглядные схемы** к модулю (архитектура, объектная модель, labels, сеть, хранение) и к конвейеру CI/CD — в файле `k8s_schemes.drawio` (лежит в корне репозитория курса): откройте на app.diagrams.net или в VS Code с расширением «Draw.io Integration».

### 8.1. Когда и для чего применяется Kubernetes

**Kubernetes (K8s)** — система оркестрации контейнеров в кластере. Появился в Google (проект Borg), с 2015 — в CNCF. Решает задачи, которые Docker Compose на одном хосте решить не может:

- размещение контейнеров на множестве нод с учётом ресурсов;
- **самовосстановление**: упавший контейнер перезапускается, умершая нода — освобождается, поды пересоздаются;
- горизонтальное **автомасштабирование** (HPA) по нагрузке;
- **rolling update и rollback** без простоя;
- сервисное взаимодействие, балансировка, хранение состояния, конфигурации и секреты.

Применять, когда: приложений больше, чем пара-тройка; нужны отказоустойчивость и масштабирование; несколько сред и команд. Для одного контейнера на одной ВМ K8s — избыточен.

### 8.2. Архитектура кластера

**Control Plane (управляющий слой)** — мозг кластера:

| Компонент | Роль |
|---|---|
| **kube-apiserver** | Единая точка входа; все команды kubectl и компоненты кластера общаются только с ним; REST API |
| **etcd** | Распределённое key-value хранилище всего состояния кластера (объекты, конфиги) |
| **kube-scheduler** | Выбирает ноду для новых подов по ресурсам, ограничениям, affinity |
| **kube-controller-manager** | Набор контроллеров: следят, чтобы фактическое состояние соответствовало желаемому (Deployment controller и др.) |
| **cloud-controller-manager** | Интеграция с облаком (LB, диски) |

**Worker-ноды (исполнители)**:

| Компонент | Роль |
|---|---|
| **kubelet** | Агент на ноде: получает от apiserver задания, запускает контейнеры через CRI (containerd/CRI-O), докладывает статус |
| **kube-proxy** | Сетевые правила (iptables/IPVS) для Services: балансировка и маршрутизация |
| **Container runtime** | containerd, CRI-O — запускает контейнеры |

Поток работы: вы применяете манифест → kubectl → apiserver сохраняет объект в etcd → контроллер видит желаемое состояние → scheduler назначает ноду → kubelet ноды запускает поды → kube-proxy настраивает сеть. **Это декларативная модель: вы описываете, ЧТО нужно, Kubernetes обеспечивает, КАК.** Схема: страница «01. Архитектура кластера» в `k8s_schemes.drawio`.

### 8.3. kubectl

**kubectl** — CLI для управления кластером.

```bash

# Просмотр

kubectl get pod myapp-6d9f5b7c8-x2v1n -o yaml # манифект объекта как в etcd

# Логи и exec
kubectl logs myapp-6d9f5b7c8-x2v1n                 # логи пода

kubectl port-forward svc/myapp 8080:80             # доступ к сервису с локальной машины

```

### 8.4. Объекты Namespace, Workload, Deployment, Pod

**Namespace** — виртуальный кластер внутри кластера: изоляция объектов, квот, RBAC между командами/проектами. Системные: `default`, `kube-system`, `kube-public`. Создание:

```bash
kubectl create namespace staging
# Или манифестом:
cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: Namespace
metadata:
  name: staging
  labels:
    environment: staging
EOF
```

**Pod** — минимальная единица развёртывания: один или несколько контейнеров, разделяющих сеть (один IP) и тома. Поды эфемерны — умирают и пересоздаются с новыми IP, поэтому **напрямую поды не используются для доступа — только через Service**.

```yaml
# pod.yaml — минимальный под (демонстрационный; в жизни используйте Deployment)
apiVersion: v1
kind: Pod
metadata:
  name: myapp
  labels:
    app: myapp           # метки — основа селекторов Service/Ingress
spec:
  containers:
    - name: app
      image: nginx:1.27  # тег обязателен (политика NeverPull не подразумевается)
      ports:
        - containerPort: 80
      resources:         # лимиты — обязательная практика
        requests:        # сколько резервируем (для планирования)
          cpu: 100m      # 100 миллиCPU = 0.1 ядра
          memory: 128Mi
        limits:          # потолок
          cpu: 500m
          memory: 256Mi
```

#### Под: от одного контейнера до sidecar-паттернов

**Под с одним контейнером** — стандартный случай: один процесс = один контейнер = один под (манифест выше). Всё, что сверх этого, — осознанное архитектурное решение.

**Почему в одном поде бывает несколько контейнеров.** Контейнеры пода всегда запускаются **на одной ноде**, делят **один сетевой namespace** (общий IP, общение через `localhost`, общий диапазон портов) и могут монтировать **общие тома**. Kubernetes управляет ими как единым целым: создаёт и удаляет одной операцией, на одной ноде. Критерий правильного разбиения: контейнеры пода должны **масштабироваться вместе** и быть **бесполезны друг без друга** — иначе это отдельные поды (отдельные Deployment'ы).

**Под с двумя контейнерами — паттерн Sidecar.** Классика: приложение пишет логи в файл, sidecar-агент читает их из общего тома и отправляет в систему сбора:

```yaml
# pod-sidecar.yaml
apiVersion: v1
kind: Pod
metadata:
  name: app-with-logger
  labels: { app: demo, pod-pattern: sidecar }
spec:
  containers:
    - name: app                       # основной контейнер: nginx пишет логи в /var/log/nginx
      image: nginx:1.27
      volumeMounts:
        - { name: logs, mountPath: /var/log/nginx }
    - name: log-shipper               # sidecar: fluent-bit читает ТОТ ЖЕ том
      image: fluent/fluent-bit:3.1    # и отправляет наружу (Elastic, Loki, CloudWatch…)
      volumeMounts:
        - { name: logs, mountPath: /logs }   # у контейнеров разные mountPath допустимы
  volumes:
    - name: logs
      emptyDir: {}                    # разделяемый временный том жизненного цикла пода
```

```bash
kubectl apply -f pod-sidecar.yaml
kubectl get pod app-with-logger              # 2/2 — оба контейнера Running
kubectl logs app-with-logger -c app          # логи конкретного контейнера
kubectl exec -it app-with-logger -c log-shipper -- sh   # shell во втором контейнере
```

Другие рабочие пары: **приложение + прокси** (Envoy/NGINX: TLS, mTLS, ретраи, авторизация — приложение ходит на `localhost:15001`, ничего не зная о сети), **приложение + агент мониторинга** (сбор метрик рядом с процессом).

**Init-контейнеры** — особые контейнеры, выполняющиеся **по очереди и до успешного завершения** перед стартом основных: ожидание БД, выставление прав на том, одноразовая подготовка данных:

```yaml
spec:
  initContainers:
    - name: wait-for-db
      image: busybox:1.36
      command: ['sh', '-c', 'until nc -z db 5432; do sleep 2; done']   # ждём, пока поднимется БД
  containers:
    - { name: app, image: myapp:1.0 }
```

```bash
kubectl get pods                    # статус INIT:0/1 — init-контейнер ещё работает
kubectl logs myapp -c wait-for-db   # его логи смотрятся как у обычного контейнера
```

**Три и больше контейнеров** — комбинация паттернов: **ambassador** (прокси исходящего трафика: приложение ходит на `localhost:<ambassador>`, тот обеспечивает ретраи, TLS, балансировку к внешнему сервису) и **adapter** (преобразует интерфейс приложения под потребителя: метрики/логи в формат мониторинга). Композиция произвольна, правило одно: все контейнеры пода — единое целое с общим жизненным циклом.

> **Официальные примеры от авторов Kubernetes** — каталог `content/en/examples/pods` репозитория kubernetes/website: https://github.com/kubernetes/website/tree/main/content/en/examples/pods. Минимальные рабочие манифесты: `simple-pod.yaml` (один контейнер), `two-container-pod.yaml` (два контейнера с общим томом), `init-containers.yaml` (init-контейнеры), `share-process-namespace.yaml` (общий PID-namespace), `private-reg-pod.yaml` (образ из приватного registry), плюс подкаталоги `probe/` (пробы), `security/`, `storage/`, `qos/` и примеры affinity/toleration (модуль 10). Эталонный стиль для собственных манифестов.

**Workload-контроллеры** (управляют наборами подов): **Deployment** (stateless-приложения, rolling update — стандарт), **StatefulSet** (стейтфул: БД, кластеры), **DaemonSet** (по одному поду на каждой ноде: агенты, логгеры), **Job/CronJob** (разовые и периодические задачи).

**Deployment** — главный объект для приложений. Управляет ReplicaSet'ом (который держит число подов) и обеспечивает стратегию обновления.

```yaml
# deployment.yaml — готовый к копипасту Deployment
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
  namespace: staging
  labels:
    app: myapp
spec:
  replicas: 3                  # желаемое число подов
  revisionHistoryLimit: 5      # сколько ревизий хранить для rollback
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1              # +1 под сверх реплик на время выкатки
      maxUnavailable: 0        # не допускать недоступности
  selector:
    matchLabels:               # по каким меткам Deployment управляет подами
      app: myapp
  template:                    # шаблон пода
    metadata:
      labels:
        app: myapp
    spec:
      containers:
        - name: app
          image: registry.example.com/myapp:1.4.2
          ports:
            - containerPort: 8000
          envFrom:                        # конфигурация из ConfigMap/Secret
            - configMapRef:
                name: myapp-config
            - secretRef:
                name: myapp-secrets
          resources:
            requests: { cpu: 100m, memory: 128Mi }
            limits:   { cpu: 500m, memory: 256Mi }
          livenessProbe:        # жив ли контейнер? нет — перезапуск
            httpGet: { path: /health, port: 8000 }
            initialDelaySeconds: 10
            periodSeconds: 10
          readinessProbe:       # готов ли принимать трафик? нет — из Service
            httpGet: { path: /ready, port: 8000 }
            initialDelaySeconds: 5
            periodSeconds: 5
          startupProbe:         # для долго стартующих (медленные JVM и т.п.)
            httpGet: { path: /health, port: 8000 }
            failureThreshold: 30
            periodSeconds: 5
```

**Пробы — три типа**: `livenessProbe` (перезапуск при зависании), `readinessProbe` (включение/выключение в балансировку), `startupProbe` (защита медленного старта). Типы проверок: `httpGet`, `tcpSocket`, `exec`, `grpc`.

### 8.5. Установка Kubernetes на Rocky Linux 10 (kubeadm + containerd)

Стенд: одна control plane `k8s-cp-01` (192.168.56.10) и две воркер-ноды `k8s-w-01/02` (.11/.12). Шаги 1–3 выполняются **на всех нодах**, дальше — по подписям.

```bash
# ===== 1. Подготовка ОС (все ноды) =====
sudo dnf update -y
sudo hostnamectl set-hostname k8s-cp-01          # на воркерах: k8s-w-01, k8s-w-02
cat <<'EOF' | sudo tee -a /etc/hosts            # или настройте DNS
192.168.56.10 k8s-cp-01
192.168.56.11 k8s-w-01
192.168.56.12 k8s-w-02
EOF

# Swap kubelet'у мешает — отключаем и выбиваем из fstab
sudo swapoff -a
sudo sed -i.bak 's/^\([^#].*swap.*\)$/#\1/' /etc/fstab

# Модули ядра: overlay (для containerd) и br_netfilter (мосты → iptables)
cat <<'EOF' | sudo tee /etc/modules-load.d/k8s.conf
overlay
br_netfilter
EOF
sudo modprobe overlay && sudo modprobe br_netfilter

# Sysctl: трафик мостов проходит через netfilter, форвардинг включён
cat <<'EOF' | sudo tee /etc/sysctl.d/k8s.conf
net.bridge.bridge-nf-call-iptables  = 1
net.bridge.bridge-nf-call-ip6tables = 1
net.ipv4.ip_forward                 = 1
EOF
sudo sysctl --system

# SELinux на учебном стенде — permissive (в проде: enforcing + настроенные политики)
sudo setenforce 0
sudo sed -i 's/^SELINUX=enforcing$/SELINUX=permissive/' /etc/selinux/config

# Firewalld: открываем порты Kubernetes (на стенде можно вместо этого systemctl stop firewalld)
sudo firewall-cmd --permanent --add-port=6443/tcp        # kube-apiserver
sudo firewall-cmd --permanent --add-port=2379-2380/tcp   # etcd (control plane)
sudo firewall-cmd --permanent --add-port=10250/tcp       # kubelet
sudo firewall-cmd --permanent --add-port=10251/tcp       # scheduler
sudo firewall-cmd --permanent --add-port=10252/tcp       # controller-manager
sudo firewall-cmd --permanent --add-port=10257/tcp       # controller-manager (счётчик)
sudo firewall-cmd --permanent --add-port=10259/tcp       # scheduler (счётчик)
sudo firewall-cmd --permanent --add-port=30000-32767/tcp # NodePort
sudo firewall-cmd --reload
```

```bash
# ===== 2. containerd — контейнерный рантайм (все ноды) =====
sudo dnf config-manager --add-repo https://download.docker.com/linux/centos/docker-ce.repo
sudo dnf install -y containerd.io
sudo mkdir -p /etc/containerd
containerd config default | sudo tee /etc/containerd/config.toml
# КРИТИЧНО: единый cgroup-драйвер systemd (иначе kubelet и рантайм живут в разных cgroup
# и поды перезапускаются/OOM'ятся)
sudo sed -i 's/SystemdCgroup = false/SystemdCgroup = true/' /etc/containerd/config.toml

```


> Манифесты и скрипты установки — каталог `examples/08-10-k8s/` в репозитории курса.

**Тонкости установки:**
- **Минимум ресурсов**: control plane — 2 CPU / 2–4 ГБ RAM, воркеры — 1–2 CPU / 2 ГБ; Rocky 10 ставится с `dnf groupinstall "Minimal Install"` — лишнее (GUI, почта) выключайте.
- **SELinux**: `setenforce 0` — допустимо для стенда; в проде оставляйте enforcing и следуйте документации containerd/kubeadm по политикам (container-selinux), иначе получите `Permission denied` на соккерах и каталогах `/var/lib/kubelet`.
- **Не снимайте taint с control plane в многонодовом проде** — пользовательские поды на CP-нодах это риск для управляющего слоя.
- **Версии**: ставьте одинаковую minor-версию kubeadm/kubelet/kubectl (`dnf versionlock`); апгрейд кластера — процедура: сначала CP (`kubeadm upgrade plan/apply`), потом ноды (drain → upgrade → uncordon).
- **HA-кластер** (несколько control plane, внешний etcd/LB) через kubeadm делается сложнее — в бою используют **Kubespray** (Ansible) или управляемые решения облаков (EKS/GKE/AKS); для курса достаточно одноCP-стенда.
- Удалить ноду: `kubectl drain <node> --ignore-daemonsets --delete-emptydir-data` → на ноде `kubeadm reset -f` → `kubectl delete node <node>`.

**Дальше по курсу** всё проверяется на живом кластере: инструментарий и k9s/Lens (8.6), углублённый kubectl (8.7), справочник сущностей (8.8) и работа с метками (8.9).

#### 8.6.1. k9s — терминальный интерфейс (TUI) к кластеру

**k9s** — консольная «панель управления» Kubernetes: кластер целиком под руками без длинных команд, работает поверх вашего kubeconfig, потребляет мало ресурсов. Идеален для SSH-сессий на bastion-хостах и быстрой работы во время инцидентов.

**Установка и запуск:**

```bash
# Linux (официальный скрипт) или пакетные менеджеры:
# brew install k9s / snap install k9s / choco install k9s
curl -sS https://webi.sh/k9s | sh
k9s version

k9s                  # текущий контекст, namespace по умолчанию
k9s --context prod   # сразу в нужном контексте
k9s -n staging       # сразу в namespace
k9s --readonly       # режим «только чтение» — исключает случайные правки/удаления
```

**Модель работы**: переход к ресурсам — командой через двоеточие, действия — горячими клавишами, `?` — справка по клавишам текущего экрана.

| Задача | Клавиши |
|---|---|
| Перейти к ресурсам | `:pods` (`:po`), `:deploy`, `:sts`, `:svc`, `:ing`, `:ns`, `:no` (nodes), `:pvc`, `:cm`, `:secret`, `:job`, `:cronjob` — работает автодополнение по `Tab` |
| «Провалиться» внутрь | `Enter` — из Deployment в его поды, из пода в контейнеры |
| Описание (describe) | `d` |
| YAML объекта | `y` — как `kubectl get <obj> -o yaml` |
| Редактировать | `e` — как `kubectl edit` |
| Логи | `l` — выбор контейнера, если их несколько; автообновление в реальном времени |
| Shell в контейнер | `s` — как `kubectl exec -it ... sh` |
| Удалить / убить | `Ctrl+D` (с подтверждением) / `Ctrl+K` (kill, без grace-period) |
| Port-forward | `Shift+F` — на поде или сервисе, дальше адрес показывается в шапке |
| Фильтр списка | `/` — ввод подстроки, `Esc` — сброс |
| Сортировка по столбцу | `Shift+<буква>` — буква из заголовка столбца |
| Все namespace | `Ctrl+A` — переключатель; иначе работа в текущем |
| Переключить namespace / контекст | `:ns` / `:ctx` |
| Пульс кластера | `:pulse` — CPU/память, поды в проблемах |
| Карта связей | `:xray deploy` — Deployment → ReplicaSet → поды → контейнеры |
| Назад / выход | `Esc` / `q` |

**Типовой сценарий диагностики в k9s:** `:pods` → фильтр `/myapp` → у пода в статусе `CrashLoopBackOff` жмём `d` — смотрим события (аналог `kubectl describe`), затем `l` — читаем логи падающего контейнера, при необходимости `y` — смотрим итоговый YAML, проверяем env и volumes. Если под завис — `Ctrl+D`: контроллер (Deployment) безопасно пересоздаст его.

**Настройка:** конфигурация живёт в `~/.k9s/config.yml` — скины, размеры лог-буфера, hotbar быстрых команд; плагины (например, интеграция с **Popeye** для аудита кластера и логгеры) подключаются файлами плагинов в `~/.k9s/`.

#### 8.6.2. Lens — графический интерфейс (GUI) к кластеру

**Lens** — десктопное «IDE для Kubernetes» (приложение на Electron). Ядро открыто (OpenLens), сборка Lens Desktop добавляет магазин расширений и сервисы. Подходит для визуального контроля, графиков метрик и быстрого onboarding'а новых членов команды.

**Установка и подключение:**

```bash
# Установщик с официального сайта или пакетный менеджер:
# brew install --cask lens / snap install kontena-lens / choco install lens
# Далее — из GUI: Lens подхватывает ВСЕ кластеры из ~/.kube/config автоматически.
# Добавить ещё: кнопка «+» (Add Cluster) → вставка kubeconfig или выбор файла.
# Кластеры закрепляются в hotbar слева для мгновенного переключения.
```

**Карта интерфейса** (левая панель):

| Раздел | Что внутри |
|---|---|
| **Overview** | Сводка кластера: загрузка нод, число подов, последние события |
| **Workloads** | Pods, Deployments, StatefulSets, DaemonSets, Jobs, CronJobs — статус, рестарты, метрики; кнопки: scale ±, restart rollout, edit, delete, port-forward |
| **Networking** | Services, Ingresses, Endpoints, NetworkPolicies, Port Forwarding |
| **Storage** | Persistent Volumes, Persistent Volume Claims, Storage Classes |
| **Configuration** | ConfigMaps, Secrets (**значения показываются расшифрованными из base64 — осторожно на скриншарах!**), Resource Quotas, Limit Ranges, HPAs |
| **Nodes** | Список и детали нод, taints, ресурсы |
| **Events** | Все события кластера с фильтрами по уровню (Warning — первое место диагностики) |
| **Custom Resources** | CRD и объекты операторов |
| **Helm** | Репозитории и релизы chart'ов: просмотр, upgrade, rollback, uninstall — GUI поверх Helm (модуль 10) |

**Работа с подом**: открываете под → вкладки: **Overview** (метрики, conditions, env), **Logs** (все контейнеры пода рядом: поиск, скачивание, timestamps, автоподгрузка), **Terminal** (exec в контейнере с выбором контейнера — аналог `kubectl exec -it`), **Events**, **YAML** (правка как в `kubectl edit`).

**Метрики**: графики CPU/память требуют **metrics-server** или подключённый Prometheus (расширение); без них Lens честно показывает предупреждение — статусы и логи при этом работают.

**Типовой сценарий**: зашли → Workloads → Pods → видим `CrashLoopBackOff` → вкладка Logs → переключатель «previous container» показывает логи падающего запуска → вкладка Events подсказывает причину (нет ConfigMap? не прошла liveness?) → правим Deployment через YAML/Edit → наблюдаем rollout.

#### k9s vs Lens — что выбрать

| Критерий | k9s | Lens |
|---|---|---|
| Интерфейс | TUI в терминале | GUI-приложение |
| Потребление ресурсов | Очень низкое | Electron — сотни МБ RAM |
| Скорость операций | Мгновенная, всё с клавиатуры | Мышь + горячие клавиши |
| Метрики и графики | Ограниченно (`:pulse`) | Полноценные графики (с metrics-server/Prometheus) |
| Где уместен | SSH/bastion, инциденты, продуктив, быстрые действия | Рабочая станция, наблюдение, обучение, демо |
| Логи | В рамках текущего view | Поиск, фильтры, несколько контейнеров бок о бок |

**Практический совет**: осваивайте кластер через Lens (всё наглядно видно) и kubectl (понимание), а оперативную рутину ведите через k9s — связка закрывает 95% ежедневных задач.

### 8.7. Углублённый разбор kubectl

**Флаги, которые нужны всегда:**

| Флаг | Действие |
|---|---|
| `-n <ns>` | namespace (без него — default/current) |
| `-A`, `--all-namespaces` | все namespace |
| `-o wide\|yaml\|json\|jsonpath=...` | формат вывода |
| `-l key=value` | селектор по меткам |
| `--field-selector spec.nodeName=n1` | фильтр по полям объектов |
| `--sort-by=.metadata.creationTimestamp` | сортировка |
| `-w`, `--watch` | следить за изменениями в реальном времени |
| `--dry-run=client -o yaml` | сгенерировать манифест без применения |

```bash
# API discovery — что вообще умеет этот кластер
kubectl api-resources                     # все типы объектов (имена, короткие имена, namespaced?)
kubectl api-versions
kubectl explain deployment.spec.template  # справка по полям манифеста — лучшая «документация» внутри CLI
kubectl explain pod.spec.containers.livenessProbe

# Вывод и выборки
kubectl get pods -A -o wide --field-selector spec.nodeName=node-2
kubectl get pods -l app=myapp -o jsonpath='{.items[*].status.podIP}'
kubectl get pods --sort-by=.metadata.creationTimestamp -n staging
kubectl get events -n staging --sort-by=.lastTimestamp | tail -20
kubectl get pod myapp-xxx -o json | grep -A8 lastState      # причина ПРОШЛОЙ остановки контейнера

# Метки, аннотации, точечные правки
kubectl label pod myapp-xxx tier=frontend --overwrite
kubectl label pod myapp-xxx tier-                       # удалить метку
kubectl annotate deployment myapp change="ticket-123"
kubectl patch svc myapp -p '{"spec":{"type":"NodePort"}}'
kubectl replace -f deployment.yaml                      # полная замена (требует актуальный resourceVersion)
kubectl diff -f deployment.yaml                         # что ИЗМЕНИТСЯ в кластере до apply
kubectl apply --prune -f manifests/ --dry-run=client    # найти объекты, вышедшие из манифестов

# Обновление образа без правки файлов (оперативно; в GitOps-мире правьте манифесты)
kubectl set image deployment/myapp app=registry/myapp:1.5.0
kubectl rollout pause deployment/myapp                  # заморозить выкатку (окно для проверок)
kubectl rollout resume deployment/myapp

# Обслуживание нод
kubectl cordon node-3        # запретить НОВЫЕ поды на ноде
kubectl drain node-3 --ignore-daemonsets --delete-emptydir-data   # эвакуировать поды (для обслуживания)
kubectl uncordon node-3      # вернуть ноду в строй

# Диагностика и ожидание
kubectl debug -it myapp-xxx --image=busybox:1.36 --target=app   # эфемерный контейнер для отладки
kubectl wait --for=condition=ready pod -l app=myapp --timeout=60s
kubectl top nodes && kubectl top pods -A --sort-by=cpu
kubectl auth can-i delete deployments -n staging --as=system:serviceaccount:staging:ci   # проверка RBAC
```

**Port-forward против NodePort:** `kubectl port-forward` — туннель с вашей машины в кластер (безопасно, точечно, но держит вашу сессию); NodePort — открытый порт на всех нодах кластера (для внешних потребителей и отладки без вашего участия).

**Жизненный цикл пода — фазы:** `Pending` (нет ресурсов/образ скачивается/не назначена нода) → `Running` (≥1 контейнер запущен) → `Succeeded`/`Failed` (завершённые, для Job). **Первая диагностика — всегда `kubectl describe pod`**: секции `Events` и `Last State` называют причину: `ImagePullBackOff` — неверный тег/нет доступа в registry; `CrashLoopBackOff` — контейнер стартует и падает (смотреть `kubectl logs --previous`); `OOMKilled` — упор в лимит памяти; `CreateContainerConfigError` — отсутствует ConfigMap/Secret из env; `0/3 nodes are available` — не хватает ресурсов или не проходят ограничения (taints/affinity).

**Тонкости пода:**
- `restartPolicy`: `Always` (контроллеры: Deployment/StatefulSet), `OnFailure` (Job — перезапускать только при ошибке), `Never` — голый под/Job до победного.
- **init-контейнеры** (`initContainers`) запускаются последовательно и до старта основных: миграции, ожидание внешнего сервиса, подготовка прав.
- **QoS-классы** определяются requests/limits: `Guaranteed` (requests == limits по CPU и памяти) → `Burstable` → `BestEffort`. При нехватке памяти на ноде первыми вытесняются BestEffort — задавайте requests/limits всегда.

### 8.8. Основные сущности Kubernetes: определения и создание (CLI и манифесты)

**Теория: почему сущности устроены именно так.** Вся объектная модель Kubernetes вырастает из трёх принципов:

1. **Декларативность (desired state).** Вы описываете желаемое состояние в манифесте и кладёте его в apiserver. Вы не говорите «создай три контейнера», вы говорите «должно работать три реплики» — а как этого достичь и удержать, решает кластер.
2. **Петля реконсиляции.** Каждый контроллер бесконечно сравнивает желаемое состояние своих объектов с фактическим и устраняет расхождение: под умер → пересоздать; реплик меньше, чем в `replicas` → досоздать; нода исчезла → переназначить поды. Поэтому Kubernetes называют системой самовосстановления.
3. **Композиция простых объектов.** Сложное поведение собирается из примитивов: Deployment управляет ReplicaSet, ReplicaSet держит поды; Service при этом не знает ни про Deployment, ни про ReplicaSet — он смотрит только на метки подов. Поэтому вместо «большого объекта приложение» в K8s много маленьких сущностей, связанных не ссылками, а **селекторами**.

Из этих принципов следуют практические выводы, которые стоит проговаривать при работе с каждой сущностью: поды **эфемерны** — не жалейте их, контроллер восстановит; IP подов **нестабильны** — ходите к приложениям только через Service; метки — главный «клей» между объектами; namespace — граница изоляции и квот; конфигурация, секреты и данные живут **отдельно** от подов (ConfigMap, Secret, PVC), чтобы под можно было удалить и пересоздать где угодно.

| Сущность | Определение | Зачем нужна (какую проблему решает) |
|---|---|---|
| **Node** | Воркер-нода кластера: машина с kubelet, kube-proxy и рантаймом. В кластер попадает сама — kubelet регистрируется у apiserver. Вручную не создаётся | Рабочая лошадка: ресурсы CPU/память/диски, на которых физически живут поды. Control Plane только распоряжается |
| **Namespace** | Виртуальный кластер внутри кластера: изоляция объектов, квот и доступа между проектами/командами | Одна команда не видит и не ломает объекты другой; квоты не дают одному проекту съесть кластер; RBAC границы |
| **Pod** | Минимальная единица развёртывания: один или несколько контейнеров, разделяющих сеть (один IP) и тома. Эфемерен, IP меняется при пересоздании | Атом размещения: планировщик и контроллеры оперируют подами, а не контейнерами; sidecar-контейнеры живут рядом с приложением |
| **ReplicaSet** | Контроллер, поддерживающий заданное число одинаковых подов: упавшие пересоздаёт. Напрямую не используется — им управляет Deployment | Самовосстановление: отказ пода или ноды не меняет количество работающих реплик |
| **Deployment** | Контроллер поверх ReplicaSet: декларативное обновление подов (rolling update), история ревизий, откаты. Стандарт для stateless-приложений | Безопасные релизы без простоя и мгновенный откат; вся история версий в кластере |
| **StatefulSet** | Контроллер для стейтфул-приложений: стабильные имена подов, сетевые имена и отдельный PVC на каждую реплику, упорядоченный запуск/остановка. Для БД, кластеров, очередей | Приложениям с состоянием нужна стабильная идентичность (имя, сеть, диск), чтобы реплики могли найти друг друга после пересоздания |
| **DaemonSet** | По одному поду на каждой (подходящей) ноде: агенты сбора логов/метрик, CNI-плагины, storage-агенты | Инфраструктурные агенты должны быть на ВСЕХ нодах и автоматически появляться на новых |
| **Job** | Под (или параллельные поды), выполняющий задачу до успешного завершения. Перезапускает поды при ошибке, `backoffLimit` ограничивает попытки | Пакетные/разовые задачи (миграции, отчёты): «выполнить до победного», а не «держать запущенным» |
| **CronJob** | Job по расписанию в формате cron: бэкапы, отчёты, синхронизации | Регулярные задачи без внешнего планировщика: расписание — часть кластера, версится в Git |
| **Service** | Стабильная виртуальная точка доступа (ClusterIP + DNS-имя) к группе подов, найденных по селектору меток. Типы: ClusterIP, NodePort, LoadBalancer, ExternalName, Headless | Поды сменяются, IP плавают; Service даёт постоянный адрес и балансировку поверх «моря» одноразовых подов |
| **Endpoints / EndpointSlice** | Объекты со списком IP:port подов, попавших в Service. Заполняет контроллер автоматически — по селектору меток и readinessProbe | Мост между абстракцией Service и реальностью подов: kube-proxy балансирует именно по этим спискам |
| **Ingress** | HTTP/HTTPS-маршрутизатор входа в кластер: по host/path направляет внешний трафик на Services. Требует контроллера (ingress-nginx, traefik) | Один внешний IP и TLS-терминация для десятков сервисов вместо десятка балансировщиков |
| **ConfigMap** | Хранение неконфиденциальной конфигурации: переменные и файлы, подключаемые поду как env или volume | Конфигурация вне образа: один образ — разные значения на dev/stage/prod без пересборки |
| **Secret** | Хранение секретных данных (пароли, токены, TLS-ключи), base64. Те же способы подключения, что у ConfigMap | Секреты вне кода и образа: ротация через обновление объекта, доступ ограничивается RBAC |
| **PersistentVolume (PV)** | Кусок хранилища в кластере: NFS-шара, диск, LVM-том. Создаётся админом или динамически | Абстракция физического хранилища: приложение не знает, NFS это, облачный диск или Ceph |
| **PersistentVolumeClaim (PVC)** | Заявка пода на хранилище: «нужно N Gi, режим доступа X, класс Y». Кластер подбирает/создаёт PV | Разделение «потребитель vs админ»: разработчик просит ресурс, не зная физики хранилища |
| **StorageClass** | Шаблон динамического создания PV у конкретного провайдера хранилища (облако, Ceph, local) | Диски нужного типа (ssd/hdd, зоны) создаются автоматически по запросу |
| **ServiceAccount** | Удостоверение «для процессов»: под запускается от имени SA, SA используется для доступа к API и для imagePullSecrets | Отвечает на вопросы «кто я для API кластера» и «откуда брать образы» — вместо статических секретов в коде |

### 8.9. Взаимодействие сущностей через метки (labels)

**Метка (label)** — пара `ключ=значение`, приклеенная к объекту (обычно к поду). **Селектор (selector)** — фильтр по меткам, через который один объект «находит» другие. Это главный механизм связывания сущностей в Kubernetes: вместо жёстких ссылок на имена/IP — декларативное соответствие по меткам. Схема: страница «02. Связи сущностей через labels» в `k8s_schemes.drawio`.

**Labels vs Annotations:** метки — для селекторов (короткие, индексируются); аннотации — для инструментов и людей (длинные произвольные данные: `kubectl.kubernetes.io/...`, rewrite-правила Ingress, owner-ссылки). По аннотациям НЕ селектируют.

**Два языка селекторов:**
- **Равенство**: `app=demo`, `tier!=frontend` — используется в `matchLabels`, `kubectl -l`;
- **Множества**: `tier in (frontend,backend)`, `!version`, `version notin (v2)` — `matchExpressions`.

**Карта связей — кто кого находит по меткам:**

| Объект | Ссылка | Механизм |
|---|---|---|
| Deployment/RS/StatefulSet/DaemonSet | свои поды | `spec.selector` ↔ `template.metadata.labels` (**selector иммутабелен** у Deployment!) |
| Service | поды-эндпоинты | `spec.selector` → контроллер заполняет Endpoints/EndpointSlices |
| NetworkPolicy | поды источника/назначения | `podSelector`, `ingress.from.podSelector` |
| Pod (anti-)affinity | поды для совместного/раздельного размещения | `labelSelector` (модуль 10) |
| PodDisruptionBudget | защищаемые поды | `spec.selector` |
| kubectl | выборки | `kubectl get pods -l tier=backend` |

Обратите внимание: **Ingress → Service и HPA → Deployment ищут по имени** (не по меткам); PVC ↔ PV связываются через storageClassName/ёмкость/режимы. Метки — прежде всего язык «под ↔ всё, что на него смотрит».

**Как это работает на практике** — поднимем двухуровневый стенд и покрутим метки:

```bash
# Поды с разными метками
kubectl run fe-1 --image=nginx:1.27 --restart=Never --labels="app=shop,tier=frontend"
kubectl run fe-2 --image=nginx:1.27 --restart=Never --labels="app=shop,tier=frontend"
kubectl run be-1 --image=nginx:1.27 --restart=Never --labels="app=shop,tier=backend"
kubectl run be-2 --image=nginx:1.27 --restart=Never --labels="app=shop,tier=backend"
kubectl get pods -L tier             # показать столбец с меткой

# Service, нацеленный на ТИР, а не на конкретный под
kubectl expose pod be-1 --name=backend --port=80 --target-port=80
kubectl patch svc backend -p '{"spec":{"selector":{"tier":"backend"}}}'   # выбираем ОБА бэка по метке
kubectl get endpoints backend        # 2 IP — оба be-пода в балансировке

# Меняем метку — под ВЫПАДАЕТ из балансировки без остановки
kubectl label pod be-2 tier=cache --overwrite
kubectl get endpoints backend        # остался 1 IP (be-1)
kubectl label pod be-2 tier=backend --overwrite   # вернули — Endpoints обновились снова

# Селекторы-множества и выборки
kubectl get pods -l 'app=shop' --show-labels
kubectl get pods -l 'tier in (frontend,backend)' -o wide
kubectl get pods -l 'app=shop,tier!=frontend'      # запятая = логическое И
kubectl delete pods -l 'app=shop'                  # удаление по селектору — с осторожностью!
```

**Тот же пример манифестами** (так и живёт в Git): Deployment создаёт поды с метками, Service находит их по тем же меткам, NetworkPolicy разрешает трафик фронта к бэку — **все три объекта связаны одной парой меток**:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: backend }
spec:
  replicas: 2
  selector: { matchLabels: { app: shop, tier: backend } }   # ① ищет свои поды
  template:
    metadata: { labels: { app: shop, tier: backend } }      # ② ставит эти метки
    spec:
      containers: [{ name: be, image: nginx:1.27 }]
---
apiVersion: v1
kind: Service
metadata: { name: backend }
spec:
  selector: { app: shop, tier: backend }                    # ③ находит те же поды
  ports: [{ port: 80, targetPort: 80 }]
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: allow-frontend }
spec:
  podSelector: { matchLabels: { app: shop, tier: backend } } # ④ политика применяется к ним же
  policyTypes: [Ingress]
  ingress:
    - from:
        - podSelector: { matchLabels: { app: shop, tier: frontend } }  # ⑤ источник — фронты по метке
      ports: [{ protocol: TCP, port: 80 }]
```

**Правила, которые спасают:**
1. Селектор и метки шаблона подов в Deployment **должны совпадать точно** — рассинхрон даст `selector does not match template labels` (или молчаливую пустоту в Endpoints).
2. Поменяв метки работающего пода, вы **мгновенно меняете его сетевую судьбу**: Service и политики перестроятся без перезапуска.
3. Перед созданием Service проверьте селектор командой `kubectl get pods -l <селектор>` — ноль результатов = Service будет пустым.
4. Проверка обратной связи: `kubectl describe svc <name>` показывает `Selector` и список `Endpoints`.

**Рекомендуемые (стандартизованные) метки** — используйте их вместо самодеятельных `app/tier`:

```yaml
metadata:
  labels:
    app.kubernetes.io/name: myapp            # имя приложения
    app.kubernetes.io/instance: myapp-prod   # уникальное имя инстанса
    app.kubernetes.io/version: "2.4.1"       # версия
    app.kubernetes.io/component: backend     # роль в архитектуре
    app.kubernetes.io/part-of: shop          # система, частью которой является
    app.kubernetes.io/managed-by: helm       # чем управляется
```

## Модуль 9. Kubernetes. Хранение и сетевое взаимодействие

### 9.1. ConfigMap и Secrets

**ConfigMap** — объект для неконфиденциальной конфигурации: переменные окружения, файлы конфигов. **Secret** — то же для секретных данных (пароли, токены, сертификаты) в base64 (это кодирование, **не шифрование** — для строгого контроля нужны внешние Vault/SOPS).

```yaml
# configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: myapp-config
  namespace: staging
data:
  APP_ENV: "staging"
  LOG_LEVEL: "info"
  # Файл целиком:
  nginx.conf: |
    server {
      listen 80;
      location / { proxy_pass http://localhost:8000; }
    }
```

```bash
# Создание ConfigMap из файла или литерала
kubectl create configmap myapp-config --from-literal=APP_ENV=staging --from-file=app.properties
# Создание Secret из литералов (base64 делается автоматически)
kubectl create secret generic myapp-secrets \
  --from-literal=DB_PASSWORD='S3cret!' \
  --from-literal=API_TOKEN='tok-123'
# Создание tls-секрета для Ingress
kubectl create secret tls myapp-tls --cert=tls.crt --key=tls.key
```

```yaml
# secret.yaml (значения должны быть base64: echo -n 'S3cret!' | base64)
apiVersion: v1
kind: Secret
metadata:
  name: myapp-secrets
  namespace: staging
type: Opaque
data:
  DB_PASSWORD: UzNjcmV0IQ==
```

Подключение к поду — два способа:

```yaml
          # 1) Как переменные окружения
          envFrom:
            - configMapRef: { name: myapp-config }
            - secretRef:    { name: myapp-secrets }
          env:
            - name: DB_HOST
              value: "postgres.backend"        # обычное значение
            - name: DB_PASSWORD
              valueFrom:                        # одна переменная из Secret
                secretKeyRef:
                  name: myapp-secrets
                  key: DB_PASSWORD
          # 2) Как файлы в томе (если env не подходит: конфиги, сертификаты)
          volumeMounts:
            - name: config-vol
              mountPath: /etc/myapp            # файлы появятся в каталоге
              readOnly: true
      volumes:
        - name: config-vol
          configMap:
            name: myapp-config
        - name: secrets-vol                  # секреты тоже монтируются как файлы
          secret:
            secretName: myapp-secrets
```

**Важно**: обновление ConfigMap/Secret **не перезапускает поды** — для применения изменений нужен рестарт (rolling restart: `kubectl rollout restart deployment/myapp`). Исключение — тома, которые подхватывают изменения самостоятельно.

### 9.2. Service, Ingress, DNS, Load Balancing

**Service** — стабильная виртуальная точка доступа к группе подов (схема: страница «03. Путь трафика» в `k8s_schemes.drawio`). Поды сменяются, IP меняются, а у Service — постоянный **ClusterIP** и DNS-имя. Service находит поды по **селектору меток**.

```yaml
# service.yaml — ClusterIP (внутренний доступ)
apiVersion: v1
kind: Service
metadata:
  name: myapp
  namespace: staging
spec:
  selector:
    app: myapp               # к каким подам направлять трафик
  ports:
    - name: http
      port: 80               # порт сервиса
      targetPort: 8000       # порт контейнера
  type: ClusterIP            # по умолчанию: доступ только внутри кластера
```

Типы Service:

| Тип | Что делает | Когда |
|---|---|---|
| **ClusterIP** | Внутренний виртуальный IP | Взаимодействие сервисов между собой |
| **NodePort** | Открывает порт 30000–32767 на каждой ноде | Отладка, простые случаи |
| **LoadBalancer** | Заказывает внешний LB у облака | Публичный доступ к сервису |
| **Headless** (`clusterIP: None`) | DNS возвращает IP всех подов напрямую | StatefulSet, клиентская балансировка |

```yaml
# Headless Service для StatefulSet (postgres-0.postgres, postgres-1.postgres…)
apiVersion: v1
kind: Service
metadata:
  name: postgres
  namespace: staging
spec:
  clusterIP: None
  selector: { app: postgres }
  ports:
    - port: 5432
      targetPort: 5432
```

**DNS в Kubernetes** — CoreDNS. Формат имён: `<service>.<namespace>.svc.cluster.local`, внутри того же namespace — просто `<service>`. Поэтому приложение обращается к БД как `postgres` или `postgres.backend`.

**Ingress** — HTTP/HTTPS-маршрутизатор «входа» в кластер: один внешний IP/LB принимает трафик и по host/path раскладывает его на Services. Требует контроллера (**ingress-nginx, traefik**) и обычно классический для веба кейс: терминация TLS + маршрутизация.

```yaml
# ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: myapp
  namespace: staging
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
    cert-manager.io/cluster-issuer: "letsencrypt-prod"   # если есть cert-manager
spec:
  ingressClassName: nginx        # какой контроллер обрабатывает
  tls:                            # HTTPS
    - hosts: [staging.example.com]
      secretName: myapp-tls
  rules:
    - host: staging.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: myapp
                port:
                  number: 80
```

**Load Balancing** внутри кластера: kube-proxy распределяет трафик Service по подам (случайно/round-robin, в зависимости от режима iptables/IPVS) только на **Ready-поды** (readinessProbe).

### 9.3. PV, PVC

Проблема: поды эфемерны, а данные БД должны жить. Схема: страница «04. Хранение PV/PVC» в `k8s_schemes.drawio`. Решение — уровни абстракции хранилища:

- **PersistentVolume (PV)** — кусок хранилища в кластере (диск NFS, LVM, облачный диск), provisioned админом или автоматически.
- **PersistentVolumeClaim (PVC)** — заявка пода на хранилище: «нужно 10 Gi ReadWriteOnce». Кластер подбирает/создаёт PV под PVC.
- **StorageClass** — шаблон динамического создания PV у конкретного провайдера.

```yaml
# storageclass + pvc + pod с БД — полный пример копипаста
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: local-ssd
provisioner: kubernetes.io/no-provisioner   # локальный диск; в облаке: ebs.csi.aws.com и т.п.
volumeBindingMode: WaitForFirstConsumer     # PV создаётся на ноде, где запустился под
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: postgres-data
  namespace: staging
spec:
  storageClassName: local-ssd
  accessModes:
    - ReadWriteOnce        # RWO: один под монтирует на запись (RWM — несколько)
  resources:
    requests:
      storage: 10Gi
---
apiVersion: apps/v1
kind: StatefulSet           # для БД — StatefulSet, не Deployment
metadata:
  name: postgres
  namespace: staging
spec:
  serviceName: postgres     # headless service (см. выше)
  replicas: 1
  selector:
    matchLabels: { app: postgres }
  template:
    metadata:
      labels: { app: postgres }
    spec:
      containers:
        - name: postgres
          image: postgres:16-alpine
          env:
            - name: POSTGRES_PASSWORD
              valueFrom: { secretKeyRef: { name: myapp-secrets, key: DB_PASSWORD } }
          ports:
            - containerPort: 5432
          volumeMounts:
            - name: data
              mountPath: /var/lib/postgresql/data
  volumeClaimTemplates:      # PVC на каждую реплику автоматически
    - metadata:
        name: data
      spec:
        accessModes: [ReadWriteOnce]
        storageClassName: local-ssd
        resources:
          requests: { storage: 10Gi }
```

**AccessModes**: `ReadWriteOnce (RWO)` — один нод на запись; `ReadOnlyMany (ROX)`; `ReadWriteMany (RWX)` — несколько нод. Ключевая идея модуля: **эфемерные поды + постоянные PVC = переживаемые данные**.

### 9.4. Тонкости хранения и сетевого взаимодействия

**Обновление ConfigMap/Secret — три разных поведения:**
1. Как env (`envFrom`, `valueFrom`): не обновляется никогда — env фиксируются при старте процесса.
2. Как volume: обновляется автоматически — kubelet синхронизирует файлы примерно раз в минуту.
3. Как `subPath` volume: **не обновляется** — subPath монтируется один раз при создании пода.
После изменения конфигурации обычно нужен `kubectl rollout restart deployment/myapp`, чтобы приложение перечитало значения.

**Secret подробнее:** поле `stringData` позволяет писать значения открытым текстом (apiserver сам закодирует в base64 при записи). Secret'ы читают все, у кого есть RBAC-право `get secrets` в namespace — ограничивайте его; для серьёзной защиты — внешние хранилища (HashiCorp Vault + External Secrets Operator). **base64 — кодирование, не шифрование**: etcd шифрует Secrets на диске только при включённой EncryptionConfiguration.

**Service — детали, о которых часто спрашивают:**
- `sessionAffinity: ClientIP` — прилипание сессии к одному поду (для старых приложений с состоянием в памяти).
- `externalTrafficPolicy: Local` (для NodePort/LoadBalancer) — трафик принимает только нода, где живёт под: сохраняется исходный IP клиента, но соединения к нодам без подов обрываются; `Cluster` (по умолчанию) — наоборот.
- `type: ExternalName` — DNS CNAME без проксирования: имя сервиса указывает на внешний адрес (этапный ход при выносе сервиса из кластера: приложение продолжает ходить на `legacy-db.staging.svc`, а CNAME уже снаружи).
- kube-proxy обновляет правила балансировки по мере изменения Endpoints (готовые поды): **readinessProbe — реальный gate попадания в балансировку**.
- Headless + StatefulSet: стабильные DNS-имена реплик `<pod-name>.<service>.<ns>.svc.cluster.local` — `postgres-0.postgres.backend`.

**Ingress — практика:**
- Аннотации зависят от контроллера (nginx, traefik, haprove — разные префиксы и возможности; смотрите документацию именно вашего).
- `pathType`: `Exact` (точное совпадение), `Prefix` (по префиксу), `ImplementationSpecific` (на усмотрение контроллера).
- В кластере может быть **несколько контроллеров** — тогда `ingressClassName` обязателен, иначе Ingress может никем не обрабатываться.
- Для автоматического HTTPS ставят **cert-manager**: он по аннотации (см. пример в 9.2) сам выпускает и продлевает сертификаты Let's Encrypt.

**PV/PVC — тонкости:**
- `persistentVolumeReclaimPolicy`: **Retain** (PV сохраняется после удаления PVC — ручная чистка, безопасно для ценных данных) vs **Delete** (удаляется и диск под ним — стандарт облачных StorageClass, осторожно!).
- Расширение тома: `allowVolumeExpansion: true` в StorageClass + `kubectl patch pvc postgres-data -p '{"spec":{"resources":{"requests":{"storage":"20Gi"}}}}'` — поддержку определяет провайдер.
- `volumeBindingMode: WaitForFirstConsumer` — для local-провайдеров и топологичных дисков: PV создаётся на той ноде, куда попал под (иначе PV может оказаться «не на той ноде», и под зависнет в Pending).
- Локальные PV требуют привязки к ноде (node affinity в самом PV): под с local PV не может мигрировать со своим диском — поэтому для БД в проде предпочитают облачные диски или реплицированные системы (Ceph, Longhorn).
- StatefulSet создаёт PVC из `volumeClaimTemplates` с именами вида `data-postgres-0`: удаление StatefulSet **не удаляет** PVC (данные сохраняются), `helm uninstall` их тоже оставляет — очищайте осознанно, `kubectl delete pvc data-postgres-0`.

## Модуль 10. Kubernetes. Продвинутые объекты, Helm

### 10.1. Pod Scheduler

**Scheduler** назначает нераспределённые поды на ноды. Алгоритм: фильтрация (какие ноды ПОДХОДЯТ: ресурсы, taints, affinity) → ранжирование (какая нода ЛУЧШЕ: меньше нагрузка, locality). Направлять распределение можно несколькими механизмами:

**nodeSelector** — простейшее: под только на ноды с меткой.

```yaml
      spec:
        nodeSelector:
          disktype: ssd          # только ноды с меткой disktype=ssd
```

**Node Affinity** — расширенный nodeSelector с операторами и режимами `requiredDuringSchedulingIgnoredDuringExecution` (обязательно) / `preferredDuringSchedulingIgnoredDuringExecution` (предпочтительно).

```yaml
      spec:
        affinity:
          nodeAffinity:
            requiredDuringSchedulingIgnoredDuringExecution:
              nodeSelectorTerms:
                - matchExpressions:
                    - key: kubernetes.io/os
                      operator: In
                      values: ["linux"]
            preferredDuringSchedulingIgnoredDuringExecution:
              - weight: 100
                preference:
                  matchExpressions:
                    - key: node-role.kubernetes.io/worker
                      operator: Exists
```

**Pod Affinity / Anti-Affinity** — размещать поды рядом друг с другом (для кеша/шардов) или, что важнее, **разносить реплики по разным нодам** (отказоустойчивость!).

```yaml
      spec:
        affinity:
          podAntiAffinity:                 # НЕ размещать реплики на одной ноде
            requiredDuringSchedulingIgnoredDuringExecution:
              - labelSelector:
                  matchLabels: { app: myapp }
                topologyKey: kubernetes.io/hostname
```

**Taints и Tolerations** — обратная логика: нода «заражена» (taint), и обычные поды на неё не попадают; попадают только те, что имеют соответствующее «противоядие» (toleration). Классика: выделенные ноды под БД, специализированные пулы.

```bash
# Запачкать ноду: на неё не будут назначаться обычные поды
kubectl taint nodes node-2 dedicated=postgres:NoSchedule
# Манифест с toleration:
#   tolerations:
#     - key: "dedicated"
#       operator: "Equal"
#       value: "postgres"
#       effect: "NoSchedule"
```

### 10.2. Policy

**Политики кластера** — ограничения «что разрешено» на уровне объектов и доступа:

- **ResourceQuota** — жёсткие лимиты ресурсов на namespace (в сумме по всем объектам): CPU, память, число подов/сервисов.
- **LimitRange** — дефолтные и максимальные requests/limits для контейнеров в namespace (защита от «безлимитных» подов).
- **Pod Security Standards (PSS)** / встроенный **Pod Security Admission**: уровни `Privileged` / `Baseline` / `Restricted` — запрещают root, hostNetwork, привилегированные контейнеры и пр. (пришли на смену deprecated PodSecurityPolicy).
- **NetworkPolicy** — файрвол L3/L4 между подами: «кто кому может ходить» (требует сетевого плагина: Calico, Cilium).

```yaml
# resourcequota.yaml — квоты namespace
apiVersion: v1
kind: ResourceQuota
metadata:
  name: staging-quota
  namespace: staging
spec:
  hard:
    requests.cpu: "4"
    requests.memory: 8Gi
    limits.cpu: "8"
    limits.memory: 16Gi
    pods: "20"
---
# networkpolicy.yaml — только поды с меткой app=frontend могут ходить в БД
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend-to-db
  namespace: staging
spec:
  podSelector:
    matchLabels: { app: postgres }        # на ком политика
  policyTypes: [Ingress]
  ingress:
    - from:
        - podSelector:
            matchLabels: { app: frontend }
      ports:
        - protocol: TCP
          port: 5432
```

### 10.3. Replication Controller

**ReplicationController (RC)** — исторический объект обеспечения числа реплик подов: держит заданное количество одинаковых подов, пересоздаёт упавшие. Устарел (уступил место **ReplicaSet** с поддержкой множественных селекторов и затем Deployment, который надстраивается над ReplicaSet и добавляет rolling update/rollback). RC остаётся в темах курса для понимания эволюции.

```yaml
# replicationcontroller.yaml — демонстрационно (в работе используйте Deployment)
apiVersion: v1
kind: ReplicationController
metadata:
  name: myapp-rc
spec:
  replicas: 3
  selector:                     # селектор — ТОЛЬКО равенство меток
    app: myapp
  template:
    metadata:
      labels: { app: myapp }
    spec:
      containers:
        - name: app
          image: nginx:1.27
          ports: [{ containerPort: 80 }]
```

**ReplicaSet vs Deployment**: ReplicaSet управляет репликами, но сам не умеет обновлять шаблон пода — меняете `image` в RS вручную, ничего не происходит. Deployment изменяет свой ReplicaSet на новый и проводит **rolling update** со стратегией `maxSurge/maxUnavailable`, сохраняя историю ревизий для отката. Поэтому в реальной работе: **только Deployment**.

### 10.4. Основы Helm

**Helm** — пакетный менеджер для Kubernetes (как apt/yum для манифестов). Единица — **chart**: шаблонизированные манифесты + значения по умолчанию. Chart можно версионировать, публиковать в репозиториях и устанавливать релизами с разными наборами параметров.

Структура chart:

```
myapp/
├── Chart.yaml          # имя, версия chart, версия приложения
├── values.yaml         # значения по умолчанию (переопределяемые при установке)
├── templates/
│   ├── deployment.yaml # шаблон с плейсхолдерами {{ .Values... }}
│   ├── service.yaml
│   ├── ingress.yaml
│   ├── configmap.yaml
│   └── _helpers.tpl    # именованные шаблоны/фрагменты
└── .helmignore
```

```yaml
# Chart.yaml
apiVersion: v2
name: myapp
description: My application chart
type: application
version: 1.0.0          # версия chart
appVersion: "2.4.1"     # версия приложения внутри
```

```yaml
# values.yaml — параметры среды по умолчанию
replicaCount: 2
image:
  repository: registry.example.com/myapp
  tag: "2.4.1"
  pullPolicy: IfNotPresent
service:
  type: ClusterIP
  port: 80
ingress:
  enabled: true
  host: staging.example.com
resources:
  requests: { cpu: 100m, memory: 128Mi }
  limits:   { cpu: 500m, memory: 256Mi }
```

```yaml
# templates/deployment.yaml — шаблон с подстановкой значений
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Release.Name }}              # имя релиза (инстанса chart)
  labels:
    app: {{ .Chart.Name }}
spec:
  replicas: {{ .Values.replicaCount }}
  selector:
    matchLabels:
      app: {{ .Chart.Name }}
  template:
    metadata:
      labels:
        app: {{ .Chart.Name }}
    spec:
      containers:
        - name: {{ .Chart.Name }}
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
          imagePullPolicy: {{ .Values.image.pullPolicy }}
          ports:
            - containerPort: 8000
          resources:
            {{- toYaml .Values.resources | nindent 12 }}   # вставка блока с отступом
          envFrom:
            - configMapRef:
                name: {{ .Release.Name }}-config
```

```bash
# Создать каркас chart
helm create myapp

# Проверка шаблонов без применения: видно, что реально уйдёт в кластер
helm template myapp ./myapp

# Установка релиза (инстанса) с переопределением значений
helm install myapp-staging ./myapp -n staging
helm install myapp-prod ./myapp -n production \
  --set image.tag=2.4.2 --set replicaCount=4 \
  --set ingress.host=example.com

# Обновление релиза (после правки values или chart)
helm upgrade myapp-staging ./myapp -n staging --set image.tag=2.4.3

# История, откат, удаление
helm history myapp-staging -n staging
helm rollback myapp-staging 1 -n staging        # откат к ревизии 1
helm uninstall myapp-staging -n staging

# Репозитории
helm repo add bitnami https://charts.bitnami.com/bitnami
helm repo update
helm search repo nginx
helm install my-nginx bitnami/nginx -n staging  # установка готового chart

# Статус, значения, дебаг рендеринга
helm list -A
helm get values myapp-staging -n staging
helm status myapp-staging -n staging
```

> Готовый чарт — `examples/08-10-k8s/helm/myapp/` в репозитории курса.

**Зачем Helm в проде**: один chart — на все среды (dev/staging/prod отличаются только values); версионирование релизов и откаты из коробки; зависимости между chart'ами (umbrella-chart со стеком приложения); стандарт де-факто для поставки приложений в Kubernetes, включая CI/CD (деплой из GitLab: `helm upgrade --install`).

**Связка модулей 6–10 в единый цикл**: коммит → GitLab CI (модуль 6) → сборка и проверка образа (модуль 7) → `helm upgrade --install` в кластер Kubernetes (модули 8–10) → наблюдаемость и откат при необходимости.

### 10.5. Тонкости Helm

**Ловушка типов в values:** числа, похожие на версии, теряют смысл — `image.tag: 1.10` может превратиться в `1.1` при неявных преобразованиях; всегда кавычки: `tag: "1.10"`. В `--set` запятые и точки внутри значения требуют экранирования: `--set 'servers={a,b}'`, `--set 'config.app\.debug=true'`.

**Идемпотентный деплой из CI — одна команда на все случаи:**

```bash
helm upgrade --install myapp-staging ./myapp -n staging \
  --set image.tag="$CI_COMMIT_SHORT_SHA" --wait --timeout 300s
```

`--install` создаст релиз, если его нет; `--wait` дождётся готовности подов (иначе команда завершится сразу после отправки манифестов в кластер); `--atomic` — при неудаче автоматически откатить изменения; `--cleanup-on-fail` — удалить созданные новые ресурсы при провале.

**Хуки — job'ы вне жизненного цикла релиза:** `pre-install`, `post-install`, `pre-upgrade`, `post-upgrade`, `pre-delete`, `post-delete`, `test`:

```yaml
# templates/migration-hook.yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: {{ .Release.Name }}-migrate
  annotations:
    "helm.sh/hook": pre-upgrade,pre-install    # когда запускать
    "helm.sh/hook-weight": "10"                # порядок между хуками
    "helm.sh/hook-delete-policy": before-hook-creation,hook-succeeded
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migrate
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
          command: ["python", "manage.py", "migrate"]
```

Важно: хуки не входят в `helm rollback` — проектируйте миграции идемпотентными и совместимыми со старой версией приложения (expand/contract-миграции).

**Зависимости chart'ов (umbrella-структура):**

```yaml
# Chart.yaml
dependencies:
  - name: postgresql
    version: 15.5.x
    repository: https://charts.bitnami.com/bitnami
    condition: postgresql.enabled      # включается из values
    tags: [db]
    # alias: db                        # переименовать зависимость в релизе
```

```bash
helm dependency update ./myapp      # скачать зависимости в charts/
helm dependency list ./myapp        # что подключено
helm template . --debug             # отрендерить вместе с зависимостями
```

**Полезные команды и плагины:**

```bash
helm lint ./myapp                   # проверка chart'а — обязательный шаг CI
helm package ./myapp                # myapp-1.0.0.tgz
helm push myapp-1.0.0.tgz oci://registry.example.com/charts   # публикация в OCI-регистри (Harbor, GitLab, Docker Hub)
helm plugin install https://github.com/databus23/helm-diff
helm diff upgrade myapp-staging ./myapp -n staging   # diff ДО применения — главный инструмент контроля
helm get manifest myapp-staging -n staging           # что реально развёрнуто
helm get values myapp-staging -n staging --all       # все values (включая дефолты)
helm history myapp-staging -n staging --max 10
```

**Шаблоны: `include` vs `template`.** `{{ template "name" . }}` вставляет текст без возможности дальнейшей обработки; `{{ include "name" . }}` возвращает строку — её можно пропустить через `nindent`, `indent`, `quote`. Канонический паттерн для меток:

```yaml
{{- define "myapp.labels" -}}
app: {{ .Chart.Name }}
release: {{ .Release.Name }}
{{- end }}

metadata:
  labels:
    {{- include "myapp.labels" . | nindent 4 }}
```

`{{ required "image.tag обязателен!" .Values.image.tag }}` — явная ошибка рендеринга при отсутствии критичного значения (падает в CI, а не в кластере); `{{ .Values.replicaCount | default 2 }}` — дефолт.

**Практика секретов в values:** не коммитьте открытые значения — пары `helm-secrets` (SOPS) или внешние операторы (External Secrets). Values подставляются в манифесты открытым текстом.

**Хранение состояния:** Helm 3 хранит всё в Secret'ах кластера (namespace релиза) — бэкапите etcd; история ревизий ограничивается `--history-max` (по умолчанию 10), `helm uninstall` с `--keep-history` сохраняет возможность отката.
